# Internationalisation (i18n)

> 中文版：[I18N.md](I18N.md)

MyFriend ships its UI in **Chinese (default / base)** and **English**. The language follows the system, there is no in-app language switch, and any system language other than English falls back to Chinese.

## Language selection

| Platform | Mechanism |
| --- | --- |
| Android | Base resources in `res/values/` are Chinese; English lives in `res/values-en/`. An English system locale picks `values-en`; any other locale (Japanese, for example) falls back to `values`. `AndroidManifest.xml` declares `zh` / `en` through `android:localeConfig="@xml/locales_config"`, so Android 13+ users can pick MyFriend's language in the system per-app language settings. No `resConfigs` restriction is used. |
| iOS | `Bundle.main` resolves the `.lproj` matching the system language. `ios/Config/Info.plist` sets `CFBundleDevelopmentRegion = zh-Hans` and `CFBundleLocalizations = [zh-Hans, en]`; the project's `knownRegions` contains `zh-Hans`, `en` and `Base`. iOS 13+ also allows choosing the language per app under Settings → app → Language. |

Neither platform implements an in-app switch: language belongs to the device environment, not to persona settings.

## Resource locations

**Android**

```
app/src/main/res/
├── values/strings.xml            Chinese (base, default)
├── values/seed.xml               Seed persona copy (Chinese)
├── values-en/strings.xml         English
├── values-en/seed.xml            Seed persona copy (English)
└── xml/locales_config.xml        zh / en declaration
```

`values-night/`, `values-v27/` and `values-night-v27/` contain only colours and themes, no language-specific strings.

Current size (the files are authoritative): Android has 876 entries per `strings.xml` (856 `<string>` + 20 `<plurals>`; Chinese plurals have only `other`, English has `other` on all and `one` on some) and 12 per `seed.xml` (3 personas × name / description / category / prompt), plus one language-dependent integer resource `usage_tokens_compact_divisor` (10000 for Chinese, 1000 for English) and date/time patterns such as `common_clock_pattern` (Chinese `HH:mm` / `M月d日`, English `h:mm a` / `MMM d`). These need no translation but must exist in both languages. On iOS each `Localizable.strings` has 557 entries (541 keys + 16 English `.one` variants) and each `InfoPlist.strings` has 1 entry; the SwiftUI layer has roughly 637 localisation call sites.

**iOS**

```
ios/MyFriend/Resources/
├── zh-Hans.lproj/Localizable.strings   Chinese (except one semantic key, key and value are the Chinese source text)
├── zh-Hans.lproj/InfoPlist.strings     Copy for system permission prompts
├── en.lproj/Localizable.strings        English (keys identical to the Chinese file)
└── en.lproj/InfoPlist.strings          English permission copy
```

iOS uses the **Chinese source text as the key** (the only semantic key is `prompt_language_directive`, named after Android's `R.string.prompt_language_directive`). The Chinese bundle is therefore an identity mapping, the English bundle only supplies translations for the same keys, and `NSLocalizedString("他发来一条消息", ...)` stays readable at the call site.

## Rules for new strings

1. **Change both files at once**: Android updates `values/strings.xml` and `values-en/strings.xml`; iOS updates `zh-Hans.lproj` and `en.lproj`. Updating only one side turns the guard tests red.
2. **Key sets and placeholders must match**: the same key must exist in both language files, and placeholders such as `%1$s` / `%2$d` must match as a set (no dropped arguments; English may reorder them, but types must correspond), otherwise runtime formatting crashes.
3. **Naming**: Android uses snake_case with a screen/component prefix — `home_` / `chat_` / `search_` / `persona_` / `memory_` / `proactive_` / `evolution_` / `preset_` / `settings_` / `about_` / `api_` / `browser_` / `backup_` / `usage_` / `common_` / `seed_` / `prompt_`. iOS keys are the Chinese source text and need no namespace.
4. **No hard-coded strings in UI code**: the UI layer only references resources — `stringResource(R.string.…)` / `context.getString(…)` on Android; `L()` / `Lf()` / `Lcount()` on iOS (defined in `ios/MyFriend/App/Localization.swift`, wrapping `NSLocalizedString`; `Lcount` handles singular/plural variants).
5. **User-visible strings in shipped code** (notification titles and bodies, settings descriptions, error messages, buttons, empty states) must live in resources; model-facing copy, logs and debug output must not.

## What is not translated

The following stay in Chinese and do **not** enter the localisation resources:

- **Code comments**: comments explain design trade-offs and their audience is maintainers;
- **Logs and debug output** (including `debug.log`, `[chat]` logs, test output);
- **Model-prompt scaffolding**: system-prompt fragments, tool descriptions, capability lists, memory extraction and consolidation prompts and reflection/scoring prompts, in both `ios/MyFriendKit` and Android `domain/`;
- **Data contracts**: JSON field names, tool names (`remember` / `recall` / `defer_reply` …), enum values, Room / SQLite table and column names, the backup's `format` / `formatVersion`;
- **Reference server**: mock responses and logs in `harness/server.mjs`;
- **Test code**: test names and assertion messages.

The reason: these strings are part of the **protocol and implementation**. Translating them would change behaviour, tests and cross-platform contracts without benefiting users. Apart from the language directive, prompt scaffolding must not follow the UI language, or model behaviour would diverge between platforms.

## Model language: the language-directive section

The prompt scaffolding is not translated, but the model still has to speak the user's language. Both platforms append a "language directive" to the **end** of the system prompt, asking the model to answer in the language the user is currently using. It is the only prompt fragment tied to the UI language that is not ordinary UI copy.

| Platform | Template location | Language | Notes |
| --- | --- | --- | --- |
| Android | `prompt_language_directive` in `values/strings.xml` and `values-en/strings.xml` | Follows the UI language: Chinese UI appends `## 语言` plus a Chinese body, English UI appends `## Language` plus an English body | Assembled by `LanguageDirective.section(…)` as the last step of building `system` in `ChatRepository`; the language name comes from `LanguageDirective.languageName()`, which uses the language without the region (`zh-CN` → 「中文」, `en-US` → 「English」) |
| iOS | The semantic key `prompt_language_directive` in `Localizable.strings` | Follows the UI language; the template wording is identical to Android | `AppLanguage.languageDirective` reads the template and language name and hands them to `PromptBuilder`; Kit reads neither resources nor `Locale` and only assembles the section. The placeholder follows iOS `String(format:)` syntax as `%1$@` (Android uses `%1$s`); meaning is the same |

Both platforms use the **same template text**; only the placeholder syntax differs. Localising the directive with the UI language is a deliberate exception for this one prompt fragment — the rest of the scaffolding (tool descriptions, capability lists, memory extraction and consolidation prompts) stays Chinese.

Other conventions:

- The section is fixed at the end of `system`, which makes it easy for tests to assert that the prompt ends with it;
- It is an **instruction**, not a hard constraint: the model may still pick the wrong language or mix languages, which is accepted rather than post-processed;
- Conversation language and UI language are independent: a user can chat in Chinese with the English UI, and the model should follow **the user's message**.

## Resource consistency guards

| Platform | Test | Assertion |
| --- | --- | --- |
| Android | `app/src/test/java/com/myfriend/app/i18n/StringResourceParityTest.kt` | String key sets are identical between `values` and `values-en`; placeholders for the same key match; plural forms are validated per language (Chinese only `other`, English must have `other` and may add `one`) |
| Android | `app/src/test/java/com/myfriend/app/i18n/ChineseLiteralGuardTest.kt` | Kotlin sources under `ui/` and `util/` contain no Chinese string literals except in comments, logs and an explicit whitelist |
| Android | `app/src/test/java/com/myfriend/app/i18n/LanguageDirectiveTest.kt` | Under both Chinese and English, the system prompt ends with the language-directive section |
| iOS | `ios/MyFriendKit/Tests/MyFriendKitTests/I18N/LocalizationResourceTests.swift` | Both `Localizable.strings` files have equal key sets and no duplicate keys; placeholder sets match per key (English may reorder, but may not drop arguments); `.one` variants are paired; every key used through `L` / `Lf` / `Lcount` / `NSLocalizedString` exists and no dead keys remain; `prompt_language_directive` matches Android verbatim; both `InfoPlist.strings` files stay in sync |
| iOS | `ios/MyFriendKit/Tests/MyFriendKitTests/I18N/UIChineseLiteralGuardTests.swift` | Chinese in `ios/MyFriend/Views/**` and `ios/MyFriend/App/**` appears only in comments, logs and an explicit whitelist |

The guards run together with the business tests (`./gradlew :app:testDebugUnitTest`, `swift test --disable-sandbox`); there is no separate i18n pipeline.

## Seed personas

Seed personas written on first install come in two sets: Chinese locales get 林深 / 阿岚 / 墨 on both platforms; English locales get native English personas — currently Elias / Finn / Ansel on Android and Rowan / Juno / Ellis on iOS (each platform maintains its own copy in `SeedPersonas`; seeds do not participate in backup interop). Seeding runs once, only when the persona table is empty and has never been seeded; switching the system language afterwards never reseeds, never rewrites existing personas, and involves no database migration. Language only affects what the first meeting looks like.

## Adding another language

1. Android: add `res/values-<locale>/strings.xml` and `seed.xml`, and add the locale to `res/xml/locales_config.xml`. `StringResourceParityTest` currently compares against a fixed `en`; it needs to iterate over every `values-*` directory instead.
2. iOS: add `<locale>.lproj/Localizable.strings` and `InfoPlist.strings`, and add the locale to `CFBundleLocalizations` and the project's `knownRegions`.
3. The language-directive section needs the language's display name supplied by the app layer.
4. Run the guard tests on both platforms and do a visual pass to confirm nothing is mixed or truncated.

- **Tool trace titles are localised** (0.10.2): display titles/subtitles come from resources while the model-facing result text stays Chinese (`ToolResult.modelSummary`); both platforms use the same table, guarded by golden tests and a real-resource instrumented test.

## Known limitations

- **No in-app switch**: language only follows the system or the system-level per-app language setting.
- **English is a translation of Chinese**: Chinese copy is authoritative; English matches semantically but not necessarily in tone.
- **No `stringsdict` on iOS**: plurals use `.one` variants plus ordinary placeholders instead of an extra format file, so English may read awkwardly at extreme counts.
- **RTL is untested**: there is currently no right-to-left language.
- **Long-string truncation**: English is generally longer than Chinese, so narrow components need a separate pass in English — the most common visual regression after a language switch.
- **Model language is instruction-level**: see above; no output post-processing is applied.
- **Kit user-visible copy is localised as of 0.10.0**: `String(localized:)` uses the Chinese source text as the key, SPM tests fall back to that key when no resources are loaded, and the app resolves it through the two `Localizable.strings` files. This covers presence, mood words, the sleep status line, tool action titles, backup/reset summaries, notifications, memory drawers and network errors.
- **Since 0.10.1, structured errors replace Chinese copy**: `data/` and `network/` only throw `UserError` (`Domain(code, arg, number)` / `Network(kind)`) and the UI maps them through `ui/common/ErrorText.kt`. Persisted values (`messages.errorMessage`, `ToolTraceItem.detail`, `proactive_rules.lastError`) store ASCII tokens (`@mf-err:...` / `@rev:...`) rendered per language; Chinese values already in old databases keep displaying as-is (no rewrite, no migration). `ChineseLiteralGuardTest` now scans `data/` and `network/` too; only 18 prompt/persistence files remain whitelisted, each with a written reason.
- **Where Chinese still appears (both platforms)**: (1) **tool trace titles** (「联网搜索」, 「记住了」, from `ToolProtocol`); (2) text written by the model (mood reasons, memory bodies, persona names/descriptions) and data persisted before the upgrade; (3) prompt scaffolding, code comments and logs. The project therefore does **not** claim to be fully bilingual.
- **English seed personas differ by platform**: Android and iOS each maintain their own English set (names above); this only affects a fresh install and does not affect backup interop.
