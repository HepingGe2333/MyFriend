**最该先修的 3 条**

1. **P1-1 切换人格后，「当前打开的会话」被清成 null**（`ChatViewModel.onCleared` 无条件 `setOpenSession(null)`）：
   之后你在看的那个会话被当成没开着——未读数 +1、前台弹系统通知、预览态不标已读。正常操作（聊天页里换人）就能触发。
2. **P1-2「清空上下文」与在跑的历史压缩没有互斥**：清空之后，压缩任务会把它算好的旧对话摘要写回
   `chat_sessions.historySummary`，于是「他已经不记得那段对话」这件事又悄悄回来了（下次开聊就进 system prompt）。
3. **P1-3「删除全部数据 / 删联系人 / 备份替换」都漏清若干含用户原文的表**
   （`memory_versions`、`memory_echoes`、`agent_ticks`、`memory_vectors`、`memory_consolidations`）：
   「全删」之后磁盘里还留着记忆旧版本、候选记忆原话、他的思考留痕。

## P0

**本次未发现 P0 级别缺陷。** 下面几条是我重点去找 P0 但确认「够不上」的，写出来是为了让下一个人不用再跑一遍：

- **删会话 / 清空上下文时正在流式生成**：不会崩，也不会丢用户已发出的消息，只会留下一条孤儿助手行或一条迟到的
  半截回复（记为 P1-6）。
- **备份「替换」导入会不会把库清空**：`BackupRepository.importBundle` 在 REPLACE 分支确实是「先清后写」，
  但 `BackupSection.kt` 的确认弹窗在 `preview.isEmpty` 时只给「知道了」，**不提供合并/替换按钮**，
  所以「拿一份读不懂的备份点替换 → 全清」这条路在 UI 上被堵住了（仓库 API 本身没有这道闸，见 P2-14）。
- **迁移 v9→v10**：顺序是「补列 → 删多余会话及其消息 → 清引用的 sessionId → 补 apiConfigId → 最后建唯一索引」，
  且在 Room 的迁移事务里；有 `MyFriendDatabaseMigrationTest` 盯着，代码层面没找到会中途失败的语句。
- **全库没有外键**（`Entities.kt` 里一个 `foreignKeys` 都没有，`ON DELETE CASCADE` 全靠手写）：
  后果不是崩溃，而是「漏删就变孤儿行」——这正是 P1-3 与 P2-12 的根因。

## P1

### P1-1 切换人格后 `OpenSessionTracker` 被清空，正在看的会话被判成「没开着」

- **位置**：`ui/screens/chat/ChatViewModel.kt:709-714`（`onCleared` 里的 `chatRepository.setOpenSession(null)`）
  × `data/repo/ChatRepository.kt:525-539`（`generateAssistant` 落库后的 `markRead`/`incrementUnread`/`notifyMessage`）
  × `data/repo/ChatRepository.kt:650`（`saveFailed` 里的 `incrementUnread`）
- **触发**：聊天页 → 右上菜单「切换人格」→ 选另一个人（`ChatScreen` → `ChatEvent.OpenSession` →
  `MyFriendNavHost.onSwitchSession` → `navController.navigate(chat(new)){ popUpTo(HOME) }`）。
- **为什么错**：`openSessionId` 是**单槽全局变量**（`domain/OpenSessionTracker.kt`）。`navigate + popUpTo(HOME)`
  会把旧 Chat 的 `NavBackStackEntry` 弹掉，旧 ViewModel 在转场结束后 `onCleared()` → `setOpenSession(null)`；
  而新会话的 `setOpenSession(sessionId)` 是在新 ViewModel 的 `init`（`ChatViewModel.kt:272-279`）里，
  发生于**旧 VM 销毁之前**。于是最终状态是 `null`，新会话的 id 丢了。
  后果：正在屏幕上看的会话，任何一条助手消息落库时都会走「没开着」分支 → `incrementUnread` + 前台
  `chatNotifier.notifyMessage`（`ChatRepository.kt:536-539` 的判断是「不等」就通知），用户会看着屏幕收到一条自己正在读的消息的通知。
- **建议修法**：`onCleared` 改成 compare-and-clear：`if (chatRepository.isSessionOpen(sessionId)) chatRepository.setOpenSession(null)`；
  更好的做法是让 tracker 记「打开中的会话集合」或由 NavHost 在 destination 变化时统一维护。

### P1-2 「清空上下文」不取消在跑的历史压缩，旧摘要会被写回来

- **位置**：`data/repo/HistoryCompressor.kt:251-260`（`sessionDao.setHistorySummary(...)` 是压缩的最后一步）
  × `data/repo/ChatRepository.kt:700-721`（`clearContext` 只清 `historySummary/historySummarizedUpTo/historySummaryAt`，
  没有触碰 `HistoryCompressor` 的 in-flight 任务）× `ChatRepository.kt:543`（`historyCompressor.ensureAsync(sessionId)` 是上一轮回复后 fire-and-forget 起的）
- **触发**：长会话（`HistoryCompression.DEFAULT_MAX_VERBATIM` 之上的条数）→ 他回完一句，压缩开始跑（一次非流式 LLM 调用，数秒）→ 用户在几秒内点「清空上下文」。
- **为什么错**：压缩在开始时读了会话与消息，结束时无条件 `setHistorySummary`。清空事务先提交，压缩后提交，
  于是「消息已删、摘要回来了」：`buildContext`（`ChatRepository.kt` 的 `memoryBlock(session.historySummary, ...)`）
  会把**用户刚删掉的那段对话**当成「更早之前你记得的」继续注入 system prompt。用户的心智模型是「他不记得了」。
- **建议修法**：给 `HistoryCompressor` 加 `cancel(sessionId)`/世代号（清空、删会话、重置摘要时 bump），
  写入前比对 `session.historySummarizedUpTo` 与「开始时读到的值」，不一致就丢弃这次结果。

### P1-3 「删除全部数据 / 删联系人 / 备份替换」漏清若干含用户原文的表

- **位置**：
  - `data/repo/ChatRepository.kt:992-1004`（`wipeAllData`：messages / sessions / memories / memory_terms(孤儿) / revisions / personas / api_configs）
  - `ui/screens/settings/SettingsViewModel.kt:157-172`（`deleteAllData` 再补 `proactiveRepository.wipeAll()` + `apiUsageRepository.wipe()` + `presetRepository.wipeAll()` + `MediaStorage.clear()`）
  - `data/repo/PersonaRepository.kt:235-266`（`delete(personaId)`）
  - `data/repo/BackupRepository.kt:274-289`（REPLACE 分支的清空清单）
- **漏掉的表**（表结构见 `data/local/Entities.kt`）：
  | 表 | 内容 | `wipeAllData` | `delete(personaId)` | 备份 REPLACE |
  | --- | --- | --- | --- | --- |
  | `memory_versions` | 记忆的旧正文（`content`/`beforeContent`，整段用户信息） | ❌ | ❌ | ✅ |
  | `memory_echoes` | 只被提过一次的候选记忆 + `sourceQuote`（**原话**） | ❌ | ✅ | ✅ |
  | `agent_ticks` | 他的思考留痕（`thought`/`outcome`） | ❌ | ✅ | ❌ |
  | `memory_vectors` | 每条记忆的向量（`ByteArray`，几百 KB 级） | ❌ | ✅(仅孤儿) | ❌ |
  | `memory_consolidations` | 每日整理摘要正文 | ❌ | ✅ | ✅ |
  | `persona_pending_patches` | 旧版「等人确认」的人设补丁（含 prompt 片段） | ❌ | ❌ | ❌ |
- **为什么错**：设置页那句是「删除全部数据」（`settings_wiped`），用户预期是**磁盘上不再有他的内容**。
  `memory_versions` 尤其严重：`MemoryReconsolidator.kt:212` 每次「回忆漂移」都写一条，而它**没有任何删除路径**
  （`MemoryVersionDao` 只有 `deleteAll`/`deleteByMemory`，且 `deleteByMemory` 全仓无调用点）——它只增不减，
  而且 `PersonaRepository.delete` 也不会清它。`wipeAllData` 同时还不清 `agent_ticks`，所以「他最近在想什么」这类
  关于你的私密句子会一直在 `myfriend.db` 里。`MediaStorage.clear()` 只删文件，删不到数据库。
- **建议修法**：把「一个人格的全部派生数据」「整库清空」各自收成一个显式清单函数
  （`PersonaDataEraser` / `wipeAll`），三处删除路径共用；`memory_versions` 补 `deleteByPersona` + 在 `deleteMemory`/整理归档时按 memoryId 清。

### P1-4 导出聊天记录（单会话 / 全部会话）在主线程做数据库循环 + JSON 编码，单会话导出还在主线程写文件

- **位置**：
  - `ui/screens/chat/ChatScreen.kt:225-248`：`exportLauncher` 的回调里直接 `context.contentResolver.openOutputStream(uri).use { stream.write(file.content.toByteArray()) }`——**没有 `withContext(Dispatchers.IO)`**，ActivityResult 回调在主线程。
  - `ui/screens/chat/ChatViewModel.kt:633-639`（`exportChat()`）与 `ui/screens/settings/SettingsViewModel.kt:137-145`（`exportAllChats()`）：都在 `viewModelScope.launch` 里调用仓库，**没有切 IO**。
  - 仓库侧：`data/repo/ChatRepository.kt:921-952`（`exportSession`）与 `:954-981`（`exportAllChats`）——`sessions.map { messageDao.getBySession(...) }` 的 N 次查询、`map` 组装、`json.encodeToString` 全在**调用方上下文**里执行（Room 的 suspend 查询自己会切线程，但每次 resume 回到主线程，循环与序列化都在主线程）。
- **触发**：任何一个几百上千条的会话点「导出」；或设置页「导出全部对话」（整库，几 MB～几十 MB）。
- **为什么错**：同目录的备份路径是标准写法（`ui/screens/settings/BackupSection.kt:172-197` 用 `withContext(Dispatchers.IO)` 写文件），
  聊天导出漏了。长会话上这是几十到几百毫秒的主线程阻塞 + 一次 MB 级 `ByteArray` 分配在主线程，StrictMode 会直接报磁盘写。
- **建议修法**：把「组装 + 编码」下沉到仓库内的 `withContext(Dispatchers.IO)`，两处 UI 的写文件也统一走 IO。

### P1-5 发送被「抽记忆」阻塞：`memoryJob?.join()` 期间点发送什么都不会发生

- **位置**：`ui/screens/chat/ChatViewModel.kt:436`（`send()` 里 `memoryJob?.join()`）、`:538`、`:557`（`regenerate()`/`editUserMessage()` 同样）、
  `:492`（`memoryJob = viewModelScope.launch { extractMemory(...) }`，在 `GenerationEvent.Completed` 时启动）
- **触发**：他刚回完一句、`autoMemoryPending` 为真（每 `extractionEvery` 条消息一次，3–12）→ 抽记忆开始（一次完整的非流式 LLM 调用，走后台并发位，等位上限 20 秒 + 生成时间）→ 用户立刻发下一条。
- **为什么错**：`send()` 先 `return` 掉（`operationInFlight` 置真），然后**挂起在 `join()` 上**，最长可等到一次完整
  模型往返（含重试）；这期间 UI 无任何 loading（`isGenerating` 为 false、`operationInFlight` 没进 `ChatUiState`），
  输入框里的字不清空、按钮看着可点，再点一次会被 `if (operationInFlight) return@launch` 静默丢弃。
  用户感知是「发送键坏了」。
- **建议修法**：不要 join：`sendUserMessage` 只写一条消息，和抽记忆没有写冲突（抽取读的是历史窗口）；
  确实要串行化的话，把 job 换成「取消上一次抽取」或在 UI 上显示「正在整理记忆…」。

### P1-6 删会话 / 清空上下文与正在跑的生成没有互斥，取消后的落库会写进已删会话或清空后的会话

- **位置**：`ui/screens/chat/ChatViewModel.kt:673-678`（`deleteSession()` 不 cancel `streamJob`）、`:577-589`（`clearContext()` 先 `streamJob?.cancel()` 但**不 join**，随后立刻开事务删消息）
  × `data/repo/ChatRepository.kt:550-579`（`catch (CancellationException)` → `withContext(NonCancellable){ saveInterrupted(...) }`）、`:581-614`（`saveInterrupted`）、`:616-655`（`saveFailed`）
  × `data/repo/ChatRepository.kt:744-751`（`deleteSession` 无条件删行）
- **触发**：流式生成中 → 菜单「删除这段对话」；或流式生成中 → 「清空上下文」。
- **为什么错**：`NonCancellable` 的落库与删除事务在两条协程上无顺序保证。
  - 删会话的路径：删除事务先提交 → `saveInterrupted` 再插一条 `sessionId` 已不存在的 `messages` 行（没有外键，插得进去），
    会话预览更新被跳过；这条消息永远不可见、也永远不会被任何删除路径清掉（孤儿行 + 磁盘泄漏）。
  - 清空上下文的路径：删除事务先提交 → `saveInterrupted` 把半截回复插回**已经清空**的会话，并改写 `lastMessagePreview`，
    用户看到「清空成功」后列表里又冒出一条半截消息（`snackbar` 与后续落库的顺序是随机的）。
- **建议修法**：`deleteSession`/`clearContext` 里 `streamJob?.cancelAndJoin()`（或在仓库内用 session 级世代号/互斥锁），
  让「删除」等「取消后的收尾落库」结束；`saveInterrupted/saveFailed` 落库前校验 session 仍存在（`sessionDao.getById`）。

## P2

### P2-1 聊天图片「选了但没发出去」永久占盘

- **位置**：`ui/screens/chat/ChatViewModel.kt:370-385`（`addImages` 把图落盘后只存进 `ephemeral.images`；`removeImage`/`clearImages` 会删文件）
  × `ChatViewModel.kt:709-714`（`onCleared` 只 cancel job，**不删 `ephemeral.value.images` 里的文件**）
- **触发**：选 1–4 张图 → 直接返回（返回键 / 从通知跳去别的会话 / 切人格）→ 不发送。
- **为什么错**：文件已经在 `files/media/chat-*.jpg`（`MediaStorage.persistChatImage`），只有「点 ×」「清空」「发送成功」三条路会绑定或删除它；

### P2-2 头像「选完又取消 / 连选两张」留下孤儿文件（Android 侧未跟进 0.10.1 的 iOS 修复）

- **位置**：`ui/screens/persona/PersonaEditorScreen.kt:130-142`（选图即 `MediaStorage.persistAvatar` 落盘 + `setAvatarUri`）、`:153-156`（`requestBack` 直接 `onBack()`）
  × `ui/screens/persona/PersonaEditorViewModel.kt`（无 `onCleared` 清理）
  × `data/repo/PersonaRepository.kt:169-172`（`MediaStorage.deleteAvatar(existing?.avatarUri)` 在 `:171`，只删「数据库里旧的那张」，不删本次编辑过程中被替换掉的中间文件）
- **触发**：新建/编辑人格 → 选头像 → 取消（或不保存返回）；或选 A → 再选 B → 保存（A 成为孤儿）。
- **为什么错**：0.10.1 的修复明确只做了 iOS（CHANGELOG：「iOS：编辑器里选了新头像又取消时删除孤儿文件」）。
  Android 每操作一次就在 `files/avatars/` 落一张 ≤200KB 的 JPEG，永不回收（`MediaStorage.deleteAvatar` 只处理 DB 里引用过的路径）。
- **建议修法**：ViewModel 记住「本次编辑新建的头像路径」，取消/保存时删除未被采纳的那张（`onCleared` 兜底）。

### P2-3 `LlmConcurrencyGate` 的「取消撞上放行」补偿在已取消的协程里拿锁，可能不归还名额

- **位置**：`domain/LlmConcurrencyGate.kt:54-78`（`acquire` 的 `catch (cancel: CancellationException)` 里 `mutex.withLock { releaseLocked(lane); drainLocked() }`）
- **触发**：`LlmGatekeeper.withPermit` 的 `withTimeoutOrNull` 超时（聊天 60s / 后台 20s）刚好和某个 `release()` 放行同一个 waiter 撞上。
- **为什么错**：这段代码的意图是「位置已经算给我了，要还回去」，但它是在**已经被取消的协程**里调 `mutex.withLock`；
  `Mutex.lock()` 是可取消的，而这正是唯一会进这个分支的时刻（`drainLocked` 是在持锁的 `release()` 里 `complete()` 的）。
  一旦 `lock()` 立刻抛出取消，`releaseLocked` 不会执行：`activeTotal`/`activeBackground` 永久 +1，
  三个名额会随着这种碰撞一次一个地蒸发，最后所有 LLM 调用都排队到超时（表现为「他彻底不回话了」，日志里只有「等并发位超时」）。
  这不是必现场景（窗口很窄），但补偿逻辑在取消上下文里执行本身就是错的。
- **建议修法**：补偿放到 `withContext(NonCancellable) { mutex.withLock { ... } }`，或改成 `tryLock()` 失败时记一条待回收标记由下一次 `release` 冲抵。

### P2-4 `AgentLoop.tick` 没有互斥：三条入口可以并发想同一件事，可能发两条重复消息

- **位置**：`data/repo/AgentLoop.kt:103`（`suspend fun tick`，全函数无锁）× 调用点：
  `data/repo/HeartbeatController.kt:129`（前台服务每 30 秒一拍，命中才 tick）、
  `data/repo/AgentTickWorker.kt`（WorkManager 每 15 分钟一次，**不经过心跳的 5 分钟下限与快照缓存**，直接 tick）、
  `data/repo/ProactiveWorker.kt`（一次性规则到点，也直接 `agentLoop.tick(now)`）
- **触发**：前台服务的某一拍掷中、同时 WorkManager 的 15 分钟周期到点（或规则 Worker 到点）。
- **为什么错**：`AgentIntentRepository.canReachOut`（调用点在 `AgentLoop.kt:247-258`）是「先查今天说够没/间隔够不够 → 再发」的 check-then-act，
  两条并发的 tick 都能通过检查，然后各自 `deliver()` 一条助手消息（`AgentLoop.kt:383-427`），
  用户收到两条几乎一样的话。文档里「兜底和心跳走的是同一套判断，不会重复打扰」的假设少了一个互斥。
- **建议修法**：`AgentLoop.tick` 外面套一个进程内 `Mutex`（`tryLock` 拿不到就直接返回 `IDLE`），或把「检查 + 落库」收进一个事务。

### P2-5 规则型主动消息无条件弹通知（会话正开着也会弹）

- **位置**：`data/repo/ProactiveRepository.kt:348`（`ProactiveNotifier.notify(...)` 前没有前置判断）
  对比另外两条正确实现：`data/repo/ChatRepository.kt:536-539`（`openSessionId != sessionId || !foregroundTracker.isForeground`）、
  `data/repo/AgentLoop.kt:423-425`（`openSessionId != session.id`）
- **触发**：主动规则的触发时刻，用户正好在这个人的聊天页里读（`isSessionOpen` 为真、甚至前台）。
- **为什么错**：消息已经在屏幕上出现，同时又来一条系统通知 + 一条聚合摘要；这违反「他看着手机时不打扰」的既定不变量，
  且 `ProactiveNotifier` 的通知会被 `MainActivity` 的点击逻辑再导航一次同一个会话。
- **建议修法**：和另外两处一样加 `if (!chatRepository.isSessionOpen(session.id)) notify(...)`。

### P2-6 `createSession` 是先查后插，撞唯一索引时「首页点联系人」直接失败

- **位置**：`data/repo/ChatRepository.kt:241-269`（`latestForPersona` 为 null 才 insert）× `:271-272`（`getOrCreateForPersona` 用 `getOrThrow()`）
  × `ui/screens/home/HomeViewModel.kt`（`openContact` 的 `catch` 只弹一句错误）
- **触发**：`ensureSessionsForAll`（启动、`MyFriendApplication`）或 `AgentLoop`/`ProactiveRepository.fire`（`getOrCreateForPersona`）
  与首页点同一个联系人并发，两边都读到「没有会话」→ 后插入的一方触发 `index_chat_sessions_personaId_unique` 冲突。
- **为什么错**：`runCatching` 把 `SQLiteConstraintException` 变成 `Result.failure`，首页只显示「打开失败」并不重试，
  用户看到的是「点这个联系人没反应/报错」，再点一次才进去。数据本身没坏，但这是可自愈的错误被当成失败抛出。
- **建议修法**：插入失败时回读 `latestForPersona` 再返回（`getOrCreateForPersona` 已经是这个语义，把 `createSession` 也做成幂等）。

### P2-7 `createdAt` 由「读最新一条 + now」推算，并发写入会撞同一毫秒；`editUserMessage` 的 `deleteAfter` 只删「严格更晚」

- **位置**：`data/repo/ChatRepository.kt:1146-1150`（`nextTimestamp`）、`:666-689`（`editUserMessage` 里的 `messageDao.deleteAfter(sessionId, message.createdAt)`）、
  `data/repo/AgentLoop.kt:389-393`（`deliver` 的同款推算）、`data/local/Daos.kt`（`deleteAfter` 是 `createdAt > :after`）
- **触发**：编辑一条用户消息的一瞬间，后台/另一条路径正好落了同一毫秒的消息（`AgentLoop.deliver` 与 `sendUserMessage` 并发）。
- **为什么错**：两条消息 `createdAt` 相同 → `deleteAfter` 不会删掉「同一毫秒但实际更晚」的助手回复 →
  编辑重发后，旧回复留在列表里，且排序按 `(createdAt, id)` 随机决定，对话读起来是错位的。
- **建议修法**：`deleteAfter` 用 `(createdAt, id)` 复合条件（`createdAt > :at OR (createdAt = :at AND id != :editedId)`），
  或给 `messages` 一个会话内的自增序号。

### P2-8 停止生成时若只有工具调用、没有可见文字，会落一条空内容助手消息（界面出现空洞气泡）

- **位置**：`data/repo/ChatRepository.kt:550-579`（取消时 `if (!completed && (shownText.isNotBlank() || traces.isNotEmpty()))` → `saveInterrupted(content = shownText)`）、
  `:581-614`（`saveInterrupted` 写 `status = STOPPED`，`content` 可以是空串）
  × `ui/screens/chat/ChatScreen.kt:1244`（`content.isNotBlank()` 才渲染正文）、`:1308`（工具痕迹只在 `status == COMPLETE` 时渲染）
- **触发**：多轮工具调用期间（`ChatRepository` 在工具轮结束时会把 `shownText` 清空）用户点「停止」。
- **为什么错**：`traces` 非空但 `shownText` 为空 → 存了一条 `content=""`、`status=STOPPED` 的助手消息。
  界面上它既没有正文（1244 跳过）也没有痕迹（1308 只在 COMPLETE 渲染），就是一个空气泡；`buildContext` 也会因为
  `content.isNotBlank()` 为假而把它排除，所以它纯粹是视觉垃圾。
- **建议修法**：`saveInterrupted` 在 `partial.isBlank()` 时不要落库（或用「已停止」占位文案走资源）。

### P2-9 图片上下文的内存峰值：最多 12 张图按 ≤4MB 解码 + base64 + 拼 JSON

- **位置**：`data/repo/ChatRepository.kt:1172-1173`（`MAX_IMAGES_PER_MESSAGE = 4`、`MAX_IMAGE_MESSAGES_IN_CONTEXT = 3`）、
  `:1053-1068`（`recentImageOwners` 取最近 3 条，`:1066` 逐张 `MediaStorage.toDataUrl`）、`util/MediaStorage.kt:22`（`MAX_CHAT_IMAGE_BYTES = 4MB`）、`:160-167`（`toDataUrl`：`readBytes` + `Base64` + 字符串拼接）
- **触发**：三条消息各带 4 张 PNG（截图最容易命中：`persistChatImage` 对 PNG **不走**质量阶梯，见 `MediaStorage.kt:139-144`）→ 下一次发送。
- **为什么错**：12 × 4MB 原始字节 → base64 约 1.33 倍 → 约 64MB 的字符串，再被 `OpenAiAdapter.buildRequest` 的
  `payload.toString()` 复制一遍（≈128MB 峰值）。中端机（heap 192–256MB）这一轮直接 OOM。
- **建议修法**：PNG 也压到与 JPEG 同级的字节上限（或统一转 JPEG/WebP），并把 `toDataUrl` 的总预算（如 8MB）在装配上下文时先算好再取舍。

### P2-10 「已读」判定对每条可见消息扫一遍整个已加载窗口，翻完历史后是 O(n²)

- **位置**：`ui/screens/chat/ChatScreen.kt:955-960`（`hasAssistantAfter = state.messages.any { ... }`，在 `items(...)` 的每个气泡里）
- **触发**：把历史一直「加载更早」翻到底之后（窗口等价于全量，CHANGELOG 自己写了这个代价），再来一次流式回复。
- **为什么错**：每个可见气泡 O(n)，滚动/流式每帧重算 → 几千条消息时每帧上万次比较；
  而且 `state` 是不可变数据类，每个 SSE delta 都会让 `items` 的 lambda 重新求值。
- **建议修法**：在 ViewModel/`remember(state.messages)` 里一次性算出「最后一条非 ERROR 助手消息的 createdAt」，
  气泡里只做一次 `createdAt > lastAssistantAt` 比较。

### P2-11 主动页的时间格式硬编码 `HH:mm`，英文界面仍是 24 小时制

- **位置**：`ui/screens/proactive/ProactiveScreen.kt:595`（`AgentIntentsCard`）、`:664`（`AgentThoughtsCard`）
  对比正确实现：`util/TimeFormat.kt:22` 用 `R.string.common_clock_pattern`（中文 `HH:mm` / 英文 `h:mm a`）
- **触发**：系统语言切英文，看「他最近在想什么」/「念头窗口」。
- **为什么错**：同一个 App 里，聊天页时间戳是 `4:10 AM`，主动页是 `04:10`；`ProactiveScreen` 里紧挨着的日期用了
  `DateFormat.getBestDateTimePattern`，只有时钟这一段漏掉了（同文件 `:599` 的 `dayFmt` 是正确的）。
- **建议修法**：两处改用 `formatClock(context, timestamp)` 或读 `common_clock_pattern`。

### P2-12 会话预览 / 默认标题落库的是中文，英文界面可见（且是「新写入」而非老数据）

- **位置**：`data/repo/ChatRepository.kt:320`（`ifBlank { if (images.isNotEmpty()) "图片" }`）、`:645`（`saveFailed` 的 `ifBlank { "回复失败" }`）、
  `:1140`（`refreshPreview` 里的同一个 `"回复失败"`）、`:260`（`"与 ${persona.name} 的对话"`，`createSession` 与 `PersonaRepository.ensureSessionFor` 各一份）、`autoTitle` 兜底 `"图片"`（`:321`）
  × 首页展示：`ui/screens/home/HomeViewModel.kt`（`preview` 直接取 `lastMessagePreview`）
- **触发**：英文系统语言下，发一张纯图片消息 / 一次回复失败 / 新建人格。
- **为什么错**：`ChineseLiteralGuardTest` 把 `ChatRepository.kt` 整份白名单掉了（理由写的是「落库值，翻译会让老库值对不上」），
  但这里写的是**新数据**：英文用户会看到「图片」「回复失败」「与 Elias 的对话」。I18N.md 的「仍会看到中文」只涵盖
  模型产出与升级前数据，不涵盖新写入的界面文案。
- **建议修法**：这三类值不落中文：预览留空（界面用资源补「还没有说过话 / 图片 / 回复失败」），
  会话标题改为「人名」或落一个 `titleKind=DEFAULT` 标记由 UI 拼。

### P2-13 从检索结果跳到很久以前的消息，会把分页退化成「全量加载」，并且是 O(n²) 的读取

- **位置**：`ui/screens/chat/ChatViewModel.kt:291-324`（`startJumpToTarget` / `loadNextPageForJump` / `isJumpExhausted`，`MAX_JUMP_PAGES = 200` 在 `:725`）
  × `ui/screens/chat/ChatViewModel.kt:336-369`（`loadOlder`：每页成功后 `sinceCursor.value = Cursor(最旧一条)`）
  × `ui/screens/chat/ChatViewModel.kt:156-170`（`sinceCursor.flatMapLatest { observeMessagesFrom(...) }`）
- **触发**：检索命中一条很久以前的消息 → 点进去。
- **为什么错**：跳跃逻辑用 `loadOlder()` 一页一页往前翻（最多 200 页 = 12000 条）。每翻一页都把 `sinceCursor` 往前挪，
  `observeMessagesFrom` 于是**重新查询「从新游标到最新」的整段区间**并整体 emit：第 k 页要读 `60 × k` 行，
  合计 O(页数²) 行（12000 条时约 120 万行读取/分配），同时列表每页重排一次。
  这正是 0.10.1 引入分页要避免的峰值，只是换了一个入口。
- **建议修法**：跳跃时不要复用「窗口 = 连续区间」的模型：按 `(createdAt,id)` 直接定位目标并只加载目标前后各一页，
  或者跳跃期间用一个独立的一次性查询（`pageAround(messageId)`），成功后再把窗口收敛到目标附近。

### P2-14 其它较小的健壮性问题（合并列出）

- **Keystore 密钥失效时错误被降级成 401**：`SecretCipher.decrypt`（`data/secure/SecretCipher.kt:34-45`）失败返回 `null`，

  但全仓只有 `MainActivity.kt:78-82`（从通知进入时）调用；从首页点进同一个会话时通知不会被撤掉。
- **首屏窗口是滑动的**：`data/repo/ChatRepository.kt:209-213` + `data/local/Daos.kt:219-220`（`ORDER BY createdAt DESC LIMIT 60`）。

  这里只提醒：`hasMoreOlder` 为真时列表应给出「上面还有」的显式提示）。
- **`Base` 备份导入 API 没有「空包」闸**：`data/repo/BackupRepository.kt:213`（`importBundle`）对 REPLACE + 全空 `bundle` 没有任何拒绝，

## 我确认过但不构成缺陷的疑点

写给下一个接手的人：下面这些我逐条读过并**确认当前实现是对的**（或是有意的取舍），不用再花时间怀疑。

1. **SSE 真的会被关掉**：`network/OpenAiAdapter.kt:139-141` 用 `currentCoroutineContext().job.invokeOnCompletion { call.cancel() }`，
   加上 `finally { completionHandle.dispose(); call.cancel() }`；`flowOn(Dispatchers.IO)` 的上游 job 是采集方的子 job，
   用户点「停止」/离开页面导致 `viewModelScope` 取消时连接会被 cancel。`SseLines.readLine` 的 8MB 单行上限也是对的。
2. **并发闸的常规路径**：`LlmGatekeeper.withPermit` 用 `withTimeoutOrNull` 包 `acquire`，超时/异常/正常结束都会 `release`；
   `LlmConcurrencyGate.drainLocked` 先放行 CHAT 再放行 BACKGROUND，与规格的 3/2/1 一致（只有 P2-3 那个窄窗口例外）。
3. **一人一段的唯一索引迁移**（`MyFriendDatabase.MIGRATION_9_10`）：先删多余会话再建唯一索引，且整体在迁移事务里；
   `api_usage` 的 `(sessionId, at)` 索引也补了。
4. **备份导入是单事务**：`BackupRepository.importBundle` 的清空 + 写入都在 `database.withTransaction` 内，失败整体回滚；
   设置走 DataStore 在事务之后写，失败只降级成 warning（这是设计，不是 bug）。
5. **备份不含密钥**：`BackupBundle` 结构里没有任何 `*Cipher` 字段，导出前还有 `BackupCodec.containsSecretField` 自检；
   `BackupApiConfig.mergeInto` 保留本机 `apiKeyCipher`，`toNewEntity` 把 Key 留空。
6. **WebView 收得住**（`ui/screens/browser/InAppBrowserScreen.kt:378-392`）：JS/DOM storage 开，但 `allowFileAccess`、
   `allowContentAccess`、`allowFileAccessFromFileURLs`、`allowUniversalAccessFromFileURLs` 全关，`setSupportMultipleWindows(false)`，
   非 http(s) scheme 交给系统；`mixedContentMode = COMPATIBILITY` 是有意的取舍（不少图床仍是 http 图片）。
   `DisposableEffect` 里做了 `destroy()`，没有 WebView 泄漏。
7. **`allowInsecureHttp` 的边界**：`NetworkGuard.parseHttpUrl` 只在配置显式打开时才放行 `http`，否则抛 `HttpsRequired`；
   聊天与联网工具（`DeepSeekWebTools.resolveEndpoint`）走同一个校验，没有旁路。
8. **Keystore 用法**：AES-256/GCM/NoPadding、`setRandomizedEncryptionRequired(true)`、IV 前缀 + `GCMParameterSpec(128)` 固定别名，
   写法正确；`getOrCreateKey` 的并发首次生成有理论风险，但 `SecretCipher` 是 `@Singleton` 且实际调用点串行（保存配置、解析配置）。
9. **通知 id 不碰撞**：`util/NotificationIds.kt` 用 FNV-1a 64 折叠进彼此分开的 id 段，锁屏公开版不带正文（`ChatNotifier.publicVersion`）。
10. **已读回执的语义**：`domain/ReadReceipt.shouldShow(readAt != null && !hasAssistantAfter)` 与规格 §2.3 一致；
    `markUserMessagesRead`（`Daos.kt` 的 `readAt IS NULL` 条件）保证重复生成不会把「已读」时间一直往后推。
   免打扰不写已读、睡着写已读由 `SleepPolicy.Decision.marksRead` 决定（`ChatRepository.evaluateSleep` 附近），与 §6.2 一致。

    后者在 `if (notice != null)` 分支内，都不会 NPE。

    除了 P2-12 那几处「新写入的界面值」之外，确实是提示词/落库留痕，不是界面文案。

## 建议的修复顺序

1. **P1-1（一行即可）** → 先在 `ChatViewModel.onCleared` 改成 compare-and-clear。这是唯一一条「正常操作必然触发、且用户直接可见」的错误，
