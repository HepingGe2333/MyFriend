# 0.10.2 iOS 端只读审计（漏洞与缺陷）

> 审计对象：`0.10.1` 之后的 iOS 端（`ios/MyFriendKit/Sources` + `ios/MyFriend/{App,Views}` + `ios/Config/Info.plist`）。
> 方式：只读源码审计 + 跑单测；**没有改动任何源码、测试或配置**。
> 验证基线：`swift test --disable-sandbox` **872 条 / 0 失败**（本次实跑，exit 0）。
> 行号以审计时的文件为准，路径相对仓库根。

## 摘要

| 严重度 | 条数 | 含义 |
| --- | --- | --- |
| P0 | 1 | 并发下的事务边界失效，可导致"已经保存成功的写入被回滚"或保存直接抛错 |
| P1 | 11 | 数据被旧值覆盖、后台任务重复执行、隐私/安全闸失灵、功能与文档不符 |
| P2 | 14 | 长会话内存、错误文案、轮询唤醒、边界数据、可用性 |

**最该先修的三条**

1. **`SQLiteDatabase.inTransaction` 的嵌套深度是跨线程共享的裸计数器**（`ios/MyFriendKit/Sources/MyFriendKit/Data/SQLiteStore.swift:105,164-185`）。
   每次聊天回复之后「抽记忆」与「压缩摘要」两条后台任务都会各自开事务，与落库/导入并发时会把两个事务缝成一个，回滚会吞掉另一个线程"已成功"的写。
2. **抽记忆 / 压缩把整行会话写回，覆盖并发写入**（`Services/MemoryExtraction.swift:82,208-211`、`Services/HistoryCompressionService.swift:196,273-279`）。
   这两件事在 `ChatService.swift:654-657` 是**同时**触发的，谁后落库谁把对方的字段、以及这期间用户新消息带来的未读数/预览一起冲掉。
3. **启动与回前台各触发一次「补算」，没有任何重入保护**（`ios/MyFriend/App/MyFriendApp.swift:23-37`、`App/AppEnvironment.swift:520-529`）。
   冷启动时 `.task` 与 `scenePhase == .active` 会跑两遍 `performCatchUp()`，于是**两次心跳 / 两次每日整理**（双倍 token，可能两条主动消息 + 两条通知）。

## P0

### P0-1 事务嵌套深度不是线程安全的，并发写入会串台

- **位置**：`ios/MyFriendKit/Sources/MyFriendKit/Data/SQLiteStore.swift:101-105`（`transactionDepth` 是裸 `Int`）、`:163-185`（`inTransaction`）；写入入口 `Data/Stores.swift:50-66`（批量 upsert 自带事务）、`Chat/ChatService.swift:376-388`、`:807-823`。
- **谁在并发写同一个 `SQLiteDatabase`**（一个进程一个实例，`App/AppEnvironment.swift:79-80` 传给所有仓储）：
  - 主线程：所有 View 的同步读写（`Views/Chat/ChatViewModel.swift:115-139`、`Views/Home/HomeView.swift:233-249`）；
  - `ChatService` 的生成任务（在非隔离 async 上下文，跑在协作线程池）；
  - 心跳/自主循环（`Services/AgentLoop.swift:556-598` 的 `deliver` 会在 `inTransaction` 里写消息 + 会话）；
  - **回复落库之后同时起的两条后台任务**：`Services/MemoryExtraction.swift:199-205`（`stores.memories.upsert(toInsert)` → 事务）与 `Services/HistoryCompressionService.swift:278-279`；
  - 备份导出/导入（`Views/Backup/BackupScreen.swift:284,357` 用 `Task.detached`，`Services/BackupService.swift:331` 是一个长事务）。
- **触发条件**：任意两个线程同时进入 `inTransaction`。
- **为什么错**：`transactionDepth` 的「判断是否已在事务里 → 递增 / 清零」没有同步。两种坏结果：
  1. 两线程同时读到 `0`，都执行 `BEGIN IMMEDIATE`，后者拿到 `SQLITE_ERROR "cannot start a transaction within a transaction"` → `SQLiteError.executeFailed` 冒到业务层：`ChatService.saveAssistant` 抛错 → 一条已经流式显示了全文的回复被丢弃并显示"回复没有保存成功"；
  2. T1 已在事务里，T2 读到 `depth > 0` → 直接执行 body（不 BEGIN、不 COMMIT）→ T2 的写**并进了 T1 的事务**。T1 一旦 ROLLBACK（批量写失败、备份导入失败、进程被杀前的回滚），T2 那些"函数已返回成功、界面已经显示、`runningGenerations` 已清空"的写入**静默消失**。
  另：`transactionDepth` 本身的读写也是数据竞争（TSan 必报）。
- **建议修法**：给 `SQLiteDatabase` 加一把串行锁（或内部 `DispatchQueue`）把 `inTransaction` 整段串起来，并用 `sqlite3_get_autocommit()` 判断真实事务状态 + `SAVEPOINT` 表达嵌套，而不是自己维护计数。

## P1

### P1-1 抽记忆 / 压缩摘要把整行会话写回，覆盖并发写入（未读、预览、摘要、抽记忆计数）

- **位置**：`ios/MyFriendKit/Sources/MyFriendKit/Services/MemoryExtraction.swift:82`（读会话）、`:208-211`（整行写回）；`Services/HistoryCompressionService.swift:196`（读会话）、`:273-279`（整行写回）；触发点 `Chat/ChatService.swift:654-657`。
- **触发条件**：任何一次正常回复之后。两条后台任务同时启动，各自先读 `ChatSessionEntity`，调完模型（几百毫秒到几十秒）再把整行 `upsert`（`INSERT OR REPLACE`）。
- **为什么错**：写回的是**读时的快照**，期间发生的任何会话变更都会被回滚：
  - 用户在这几秒里又发了一条消息 → `ChatService.appendUserMessage`（`:376-388`）写了新预览、`unreadCount = 0`；抽记忆随后把预览、`lastMessageAt`、`unreadCount` 全改回旧值 → 首页预览指向一句更早的话、未读数把已经读过的消息又算一次；
  - 抽记忆与压缩互相覆盖：抽记忆的 `lastMemoryExtractedCount` 刷掉压缩写入的 `historySummary/historySummarizedUpTo`（或反之）→ 摘要白压一次（下次重新压、多花一次 token），或者同一段话被反复抽取；
  - 极端情况：这段会话/人格在等待期间被删掉，`upsert`（`INSERT OR REPLACE`）会把已删除的 `chat_sessions` 行**重新插回来**（`personaId` 唯一索引还在），出现指向不存在人格的幽灵会话。
- **建议修法**：改成"只更新自己那几个字段"的定向 `UPDATE`（`historySummary/historySummarizedUpTo/historySummaryAt` 一组、`lastMemoryExtractedCount` 一个），不要整行 REPLACE；并且在事务内重新读一次会话。

### P1-2 启动/回前台「补算」可重复触发：两次心跳、两次每日整理

- **位置**：`ios/MyFriend/App/MyFriendApp.swift:23-31`（`.task { … await env.performCatchUp() }`）与 `:32-37`（`.onChange(of: scenePhase)` 的 `.active` 又起一个 `Task { await env.performCatchUp() }`）；`App/AppEnvironment.swift:520-529`（`performCatchUp` 无重入保护，`catchUpPlan` 只是纯判定）；`Services/HeartbeatController.swift:114-183`（`beat()` 全程没有互斥）。
- **触发条件**：冷启动（`scenePhase` 由 `inactive` 变 `active` 会触发 `onChange`）、或快速前后台切换、或前台补算与 `BGProcessingTask` 时间片撞上（`App/BackgroundScheduler.swift:128-134` 里整理完还会再补一次 `runBackgroundTick`）。
- **为什么错**：两次 `performCatchUp` 都读到同一个 `lastHeartbeatAt`/`lastConsolidatedAt`，因此都判 `shouldTick/shouldConsolidate = true`；`heartbeat.beat` 的"刚想过"闸（`HeartbeatController.swift:156-158`）要在**掷骰之后**才查 `ticks.lastTickAt()`，两个并发调用都能穿过；`AgentLoop.tick` 的 `AsyncMutex`（`Services/AgentLoop.swift:83,127-128`）只保证**串行**、不做幂等去重。结果是两次 LLM 调用、两条主动消息（`AgentLoop.deliver` 各写一条）+ 两条通知，以及两条 `memory_consolidations` 记录。
- **建议修法**：`performCatchUp`/`runBackgroundTick`/`runDailyConsolidation` 外层加一个 `AsyncMutex` + "memo 本次已补算" 的最小去重，判定与写入放进同一临界区。

### P1-3 iOS 侧没有「前台每 30 秒一拍」的心跳，长会话期间他永不主动开口

- **位置**：`ios/MyFriend/App/MyFriendApp.swift`（整个 App 层没有 `Timer`/定时 Task）；`Services/HeartbeatController.swift:186-193`（`checkIntervalMillis()` 在 App 与 Kit 里**只有测试调用**，`grep` 全仓确认；`intervalMinutes()` 只在 `:152` 内部用于换算单拍概率）；唯一驱动是 `App/AppEnvironment.swift:535-546`（`runBackgroundTick`），调用方只有 `performCatchUp` 与 BGTask。
- **触发条件**：连续使用 App 超过一会儿（或前台停留时）。
- **为什么错**：`App/AppEnvironment.swift:507-514` 的判据是"距离上次想事情 ≥ 10 分钟（前台）"才补一次，且只在冷启动/回到前台时求值。于是**用户一直开着 App 聊天时，一拍都不会发生**：主动唤醒规则不会转念头、心跳不掷骰、`defer_reply` 之外那条"他主动找你"的链路在前台等于不存在。与 `docs/IOS-PARITY.md:50,71`（"前台 30 秒 + 后台 `BGAppRefreshTask`"）与 `docs/ARCHITECTURE.md:17` 的描述不符——文档当作已有能力，代码里没有。
- **建议修法**：在 App 层起一个前台 30 秒（可低电量放宽到 2 分钟）的 `Task` 循环调 `heartbeat.beat()`，或明确把文档改成"iOS 只有回前台补算"。

### P1-4 BGTask 的完成上报语义用错，且时间片到期没有兜底 `setTaskCompleted`

- **位置**：`ios/MyFriend/App/BackgroundScheduler.swift:108-119`（`handleRefresh`：`setTaskCompleted(success: acted && !work.isCancelled)`）、`:122-136`（`handleProcessing` 同理用 `consolidated`）。
- **触发条件**：每次系统给的刷新时间片，只要这一拍没有真的说话/做事（按产品设计这是**绝大多数**：`Services/HeartbeatController.swift` 注释写明"绝大多数拍什么都不会发生"）。
- **为什么错**：
  1. `setTaskCompleted(success: false)` 的含义是"任务失败"。一个正常跑完但无事可做的刷新被反复上报为失败，系统会据此降低后续调度频率（BGTaskScheduler 的已知行为），最终把后台刷新饿死；
  2. `task.expirationHandler` 只 `work.cancel()`，若 `work` 卡在门控等待（`Net/LlmConcurrencyGate.swift:151-154` 的 20/60 秒等待对取消不敏感）或长请求（`AppEnvironment.swift:600-601` 请求超时 120 秒 / 资源 900 秒）里，`setTaskCompleted` 可能在整个时间片里都到不了 → 进程被系统以"未上报完成"杀掉，并影响后续调度。
- **建议修法**：无事可做也上报 `success: true`（只有真出错才 false）；在 `expirationHandler` 里立刻 `setTaskCompleted(success: false)` 并保证只上报一次。

### P1-5 `ResilientKeychain` 的 UserDefaults 兜底在真机上同样会被触发（明文 Key 落盘）

- **位置**：`ios/MyFriend/App/ResilientKeychain.swift:20-31`（任何 `SystemKeychain.set` 失败 → `UserDefaults.standard.set(value, …)`）；读回在 `:33-40`。
- **触发条件**：真机上的任何 `SecItemAdd` 失败，例如设备锁屏未解锁时的 `errSecInteractionNotAllowed (-25308)`（`Support/Keychain.swift:58` 用的是 `kSecAttrAccessibleAfterFirstUnlock`，首次解锁前后台任务就会撞上）、或 `delete` 之后仍返回 `errSecDuplicateItem` 的异常态。
- **为什么错**：代码里没有任何"只在模拟器/未签名构建才允许兜底"的判定（没有 `#if targetEnvironment(simulator)`，也没有检查签名）。真机上兜底一旦触发，API Key 就以**明文**存在 `UserDefaults`（`Library/Preferences/*.plist`），会进 iTunes/iCloud 整机备份，而 `ApiKeyStore`（`Data/ApiKeyStore.swift:40-42`）照样能读到它，用户与开发者都无从察觉。这与 `docs/IOS-PARITY.md:107-109` 的"真机不受影响"相反；`App/AppEnvironment.swift:85-86` 的注释也把它描述成"失败才调试兜底"，但代码无条件生效。
- **建议修法**：兜底只在 `#if DEBUG && targetEnvironment(simulator)` 下编译进去；真机上失败就抛错让用户重填，并在日志里明确记录 OSStatus。

### P1-6 ATS 被全局关掉，且进的是发布配置

- **位置**：`ios/Config/Info.plist:70-79`（`NSAllowsArbitraryLoads = true` + `NSAllowsLocalNetworking = true`）。
- **触发条件**：所有构建（不是 Debug-only，`Info.plist` 只有一份）。
- **为什么错**：App 里确实还有一道代码闸（`Net/OpenAICompatibleClient.swift:106-125` 的 `NetworkGuard` 默认只放 HTTPS），但 ATS 全关意味着：① 任何非 `URLSession` 路径（WebKit、系统框架、将来接入的 SDK）都能明文出网；② 内置浏览器（`Views/Browser/InAppBrowserView.swift`）可以直接打开任意 `http://` 页面；③ App Store 审核要求为 `NSAllowsArbitraryLoads` 提供理由，通常会被要求改成域例外。注释里写的是"本地联调用"，但它不是联调专用的。
- **建议修法**：去掉全局 `NSAllowsArbitraryLoads`，只保留 `NSAllowsLocalNetworking`（或 `NSExceptionDomains` 里的本地地址例外）；用户显式打开"允许不安全 HTTP"的请求走 `URLSessionConfiguration` 侧的单次豁免。

### P1-7 备份页的「清空 / 删除全部」不清理图片与头像文件

- **位置**：`ios/MyFriend/Views/Backup/BackupScreen.swift:388-401`（`clearChats()` / `clearAll()` 只调 `env.dataReset.*`）对照 `Views/Settings/SettingsScreen.swift:678-700`（设置页同样的动作后面跟着 `MediaStorage.shared.delete(images)` / `.deleteAll()`）。
- **触发条件**：从「设置 → 备份 → 危险区」执行「清空全部聊天与记忆」或「删除全部本地数据」。
- **为什么错**：`DataReset` 的媒体清理是一个**可选回调** `onClearMedia`（`Services/DataReset.swift:106,119,141,198`），而装配层根本没传（`App/AppEnvironment.swift:267`），真正干活的是两个 View；备份页这条路径忘了。于是"全部删除"之后用户的消息、头像记录都没了，但聊天图与头像文件仍留在 `Application Support/attachments/` 里（`CHANGELOG.md:65` 声称"「清空全部数据」删头像目录"）。
- **建议修法**：把媒体清理收进 `DataReset` 的必选依赖（装配时传 `MediaStorage`），两个入口都只调 `DataReset`。

### P1-8 `MediaStorage.deleteAll()` 重建目录时丢掉「不进备份」标记

- **位置**：`ios/MyFriendKit/Sources/MyFriendKit/Support/MediaStorage.swift:501-504`（`removeItem` + `createDirectory`），对照 `:322-333`（`init` 里设 `isExcludedFromBackup = true`）。
- **触发条件**：设置页点「删除全部本地数据」（`Views/Settings/SettingsScreen.swift:695` → `MediaStorage.shared.deleteAll()`），此后用户再发图片/换头像。
- **为什么错**：新建的目录没有 `URLResourceValues.isExcludedFromBackup`，于是**清空过一次之后**，附件目录（几百 MB 聊天图 + 头像）开始进 iCloud/iTunes 整机备份。这与"图片二进制不进备份"的产品约定（`docs/IOS-PARITY.md:62`、`docs/ARCHITECTURE.md:163`）冲突，而且用户完全看不出来。
- **建议修法**：`deleteAll()` 复用一个 `applyBackupExclusion()`（把 `init` 里那段抽出来），删完重建后立刻调用。

### P1-9 合并导入会覆盖本机会话的整行与图片附件引用

- **位置**：`ios/MyFriendKit/Sources/MyFriendKit/Services/BackupService.swift:287-295`（同人会话并进本机 id，随后 `:358` 整行 `upsert`）、`:587-597`（消息转实体时**无条件** `attachmentsJson: nil`）、`:359`（`messages.upsert`）。
- **触发条件**：「从备份里接他回来 → 合并」（哪怕导入的就是同一台手机刚导出的备份）。
- **为什么错**：
  1. 会话行用备份里的 `lastMessagePreview` / `lastMessageAt` / `unreadCount` / `historySummary*` / `lastMemoryExtractedCount` 覆盖本机那条（`INSERT OR REPLACE` 是整行替换），备份比本机旧时 → 首页预览倒退、未读数被重置、摘要与抽记忆计数倒退；
  2. 消息 id 相同，REPLACE 时 `attachmentsJson` 被写成 `NULL` → **本机所有带图消息的图片引用被抹掉**（文件还在磁盘上变成孤儿），而界面提示的却是"备份里的图没跟过来"这种跨设备说法。
- **建议修法**：合并模式下会话只做 `UPDATE` 指定字段、并取"更新的一方"；消息导入时若本机同 id 已有 `attachmentsJson` 则保留（或按"备份里为空就不覆盖"）。

### P1-10 发送失败会吞掉用户的草稿与已选图片（并留下孤儿文件）

- **位置**：`ios/MyFriend/Views/Chat/ChatViewModel.swift:302-308`（先 `draft = ""`、`pendingAttachments.removeAll()`，再调 `env.chat.send`）；失败源 `Chat/ChatService.swift:331-353`（`消息过长` / `会话不存在` / `请先为该会话选择 API 配置` / `API 配置已不存在` 都在**落库之前**抛出，返回的是 `failedStream`）。
- **触发条件**：粘贴超过 32000 字的文本（输入框没有长度限制）、会话被别人删掉、或配置在发送瞬间被删除。
- **为什么错**：`send()` 在拿到流之前就清空了输入状态；`appendUserMessage` 抛错时那条流只带错误、没有落库。结果是**用户刚打的字和刚选的图不可恢复**（`pendingAttachments` 已被清空、文件已写入沙盒但没有任何消息引用），只能重打重选，同时磁盘上留下孤儿图片。
- **建议修法**：`ChatService.send` 先返回"是否已落库"，落库失败时把草稿/附件还给界面（或让 ViewModel 在失败回调里恢复 `draft` 与 `pendingAttachments`）。

### P1-11 并发闸的取消传播不完整；排队超时的错误文案不看车道

- **位置**：`ios/MyFriendKit/Sources/MyFriendKit/Net/LlmConcurrencyGate.swift:116-167`（`acquire` 用 `withCheckedContinuation`，**对 Task 取消不敏感**；`:151-165` 的超时定时器是唯一的唤醒源）；`Net/OpenAICompatibleClient.swift:344-348`（拿不到名额时用 `self.busyError(lane: .chat)` 硬编码聊天道）。
- **触发条件**：用户在"后台占用 2 个名额"时点发送后马上点停止；或用户在 60 秒排队窗口内离开页面。
- **为什么错**：
  1. `stop()` 只能取消 `ChatService` 的任务与流，取消**不会**唤醒卡在 `gate.acquire()` 里的 continuation（`Task.cancel()` 无法中断 `withCheckedContinuation`）。等待者要等到 20s/60s 超时才被摘下并 resume——期间这次"已经取消"的调用仍可能被授予名额并真的发出一次请求（`runStream` 进入前没有 `Task.isCancelled` 检查），用户已经点了停止却还在花 token；
  2. 后台道（抽记忆/整理/心跳）超时被授予的是"他手上还有别的事没忙完，这次没顾上回你…"这句面向聊天的文案，与 `docs/ARCHITECTURE.md:92` 的"后台拿不到就放弃并记日志"不一致，日志里也会误导排查。
- **建议修法**：`acquire` 改为 `withTaskCancellationHandler`（取消时把自己从 `waiters` 摘掉并 `resume(.timedOut)` 或抛 `CancellationError`），授予名额后先查 `Task.isCancelled` 再发请求；`busyError` 用 `LlmCallLane(kind:)`。

## P2

### P2-1 长会话在"每次回复 / 每次思考"里全量读历史

- **位置**：`ios/MyFriendKit/Sources/MyFriendKit/Chat/ChatService.swift:430`（`bySession` 读整段，只取 `suffix(contextRecentLimit)`）、`Services/AgentLoop.swift:662`（心跳处境里整段读）、`Services/MemoryExtraction.swift:90`、`Services/MemoryConsolidator.swift:342`。
- **为什么错**：0.10.1 只把**聊天页 UI** 窗口化了（`Views/Chat/ChatViewModel.swift:130-139`），模型/后台路径仍然 `SELECT * FROM messages WHERE sessionId = …` 后整体物化成 `[MessageEntity]`。几千条消息的会话里，每轮回复、每拍心智活动都要付一次全量分配（含 `content`/`attachmentsJson`/`toolTraceJson` 三份大字符串），这正是 `docs/ARCHITECTURE.md:186` 承认的"长会话内存最大一块"。
- **建议修法**：需要尾部时统一走 `MessageStore.recent(sessionId:limit:)`（`Data/Stores.swift:683-690`），只看"最后一次用户消息"时走精确查询。

### P2-2 错误响应体与非流式响应没有体积上限

- **位置**：`ios/MyFriendKit/Sources/MyFriendKit/Net/OpenAICompatibleClient.swift:399`、`:405`（`Self.readAll(bytes)`）、`:870-878`（`readAll` 逐字节 append，无上限）。
- **为什么错**：网关/代理返回一个没有 Content-Length、持续输出的错误页时，`readAll` 会一直往 `Data` 里塞；SSE 那条路径有 `SSEParser.MAX_LINE_BYTES = 1MB`（`Net/SSE.swift:37,54-60`）兜底，`readAll` 没有。Android 侧 0.10.1 已经给"单行 8MB 上限"补过同类护栏（`docs/CHANGELOG.md:73`）。
- **建议修法**：`readAll` 加字节上限（如 256KB/1MB），超限截断并标记为"响应过长"。

### P2-3 聊天页的 4 秒轮询与 30 秒脉冲一直在查库

- **位置**：`ios/MyFriend/Views/Chat/ChatViewModel.swift:206-243`（`startPulse` → `startMessagePulse`）、`:246-255`（每 4 秒 `count` + `latest` 两次查询）。
- **为什么错**：这两条 Task 只在 `leave()`（`onDisappear`）时停止；`isGenerating` 期间仍然每 4 秒唤醒一次并 return。长时间停留在一个聊天页会持续唤醒 CPU 与 SQLite（`count(*)` 在 `messages` 上虽走索引，但仍是全表计数）。对比 `Views/Chat/ChatScreen.swift:152-157` 已经在 `scenePhase == .active` 时重读一遍，轮询属于双保险。
- **建议修法**：进后台/无生成时把间隔拉到 15–30 秒，或在 `isGenerating` 时直接跳过整拍（`guard` 放在 `sleep` 之前）。

### P2-4 首页的未读与预览不随后台写入刷新

- **位置**：`ios/MyFriend/Views/Home/HomeView.swift:51-53`（只在 `onAppear` / `activePersonaId` 变化 / 下拉刷新时 `reload`）。
- **为什么错**：心跳/主动唤醒在用户停留首页时写消息（`Services/AgentLoop.swift:556-598`），首页的未读角标与"最后一句"不会变，用户要切走再回来才看到——与通知同时到达却不同步，容易被当成 bug。
- **建议修法**：复用聊天页那套"条数 + 最新 id"轻量比对，或订阅一个 App 层的"消息已写入"通知。

### P2-5 分页窗口会随新消息滑动，已加载的历史被悄悄挤掉

- **位置**：`ios/MyFriend/Views/Chat/ChatViewModel.swift:130-139`（`window = max(pageSize, messages.count)` 后重读"最后 window 条"）、`:177-194`。
- **为什么错**：用户上滑加载到 180 条后，只要来一条新消息，重读的就是"最后 181 条"——最前面那一页被挤掉，滚动位置跳动；如果用户已经翻到最早（`hasMoreHistory == false`），新消息又会把"加载更早"重新变出来。
- **建议修法**：重读时按"当前窗口首条消息的游标"向后扩（保持窗口上界不动），只在"跟随最新"时重置窗口。

### P2-6 未本地化的文案会直接上屏

- **位置**：`ios/MyFriendKit/Sources/MyFriendKit/Chat/ChatService.swift:705`（`message = localized.isEmpty ? "生成失败" : localized` —— 裸中文字面量，英文界面照样显示"生成失败"）；`Net/OpenAICompatibleClient.swift:809-811`（`default:` 分支把系统 `localizedDescription` 直接当用户文案，例如 `NSURLErrorBadServerResponse` → "The operation couldn't be completed…"）；`Views/Chat/ChatViewModel.swift:487` 同一模式。
- **为什么错**：`docs/I18N.md:50,51` 要求"界面层只引用资源、用户可见文案必须进资源"；Kit 层的中文字面量不在 `UIChineseLiteralGuardTests` 的扫描范围（它只扫 `ios/MyFriend/{Views,App}`），所以这类漏网会一直存在。`localizedDescription` 的语种跟系统走，英文机型上是英文、中文机型上是中文，但**与 App 界面语言无关**，且技术措辞不该给用户看。
- **建议修法**：`"生成失败"` 换成 `String(localized:)`；`mapNetworkError` 的 `default` 分支统一映射成一条资源文案，原文只进日志。

### P2-7 从通知冷启动时深链接可能丢失

- **位置**：`ios/MyFriend/App/MyFriendApp.swift:25`（`AppNotifications.shared.configure()` 在 `WindowGroup.task` 里才执行）；`App/AppNotifications.swift:44-47`（`configure()` 才设 `center.delegate`）。
- **为什么错**：`UNUserNotificationCenter.delegate` 必须在启动完成前（`didFinishLaunchingWithOptions` 返回前）设好，否则"点通知冷启动"那次响应的回调不会被投递；SwiftUI 的 `.task` 在首帧之后才跑。表现：App 没在运行时点通知 → 只打开首页，不进对应会话（`App/RootView.swift:36-41` 的 `pendingSessionId` 永远拿不到值）。
- **建议修法**：把 delegate 的装配挪到 `MyFriendApp.init()`（或一个 `UIApplicationDelegateAdaptor`），与 `BackgroundScheduler.register()` 同一时机。

### P2-8 内置浏览器：JS 常开、共享持久 Cookie、无导航白名单

- **位置**：`ios/MyFriend/Views/Browser/InAppBrowserView.swift:140-152`（`allowsContentJavaScript = true`、未设置 `WKWebsiteDataStore.nonPersistent()`、没有实现 `decidePolicyFor navigationAction`）。
- **为什么错**：入口是模型消息里的链接（`Domain/LinkDetector.swift` 已把 `file:`/`javascript:`/`data:` 挡在外面，这一层是好的），但页面内的跳转/重定向不受限：可以跳到任意 scheme、可以在会话之间共享 Cookie/LocalStorage（跨站追踪），也无法限制"只在应用内浏览"。
- **建议修法**：默认 `nonPersistent()` 数据仓；实现 `decidePolicyFor navigationAction`，只放行 http/https，其余 scheme 交给 `UIApplication.open`。

### P2-9 两处"多线程写共享状态"没有同步

- **位置**：`ios/MyFriendKit/Sources/MyFriendKit/Services/HeartbeatController.swift:170-176`（`cached = BeatSnapshot(...)` 在 `lock` **外**写，而 `snapshotFor` 在锁内读，`:206-226`）；`ios/MyFriend/App/DebugSeeding.swift:28-39`（`debug.log` 用 `FileHandle(forWritingTo:)` 无锁 append，会被背景服务与主线程同时调用）。
- **为什么错**：`cached` 是含 `String`/枚举的结构体，锁外写与锁内读并发落地是数据竞争（可能读到撕裂状态或在 ARC 上崩）；`debug.log` 并发 append 会丢行/插行，排查时误导判断（仅 DEBUG）。
- **建议修法**：`cached` 的写也放进 `mfWithLock`；`DebugSeeding.log` 用一个串行队列或静态锁。

### P2-10 `MFAvatar` 对 `avatarSeed` 取绝对值会崩

- **位置**：`ios/MyFriend/Views/Shared/MFAvatar.swift:117`（`let index = abs(avatarSeed) % Self.palette.count`）。
- **触发条件**：`personas.avatarSeed` 为 `Int.min`。这个值可以从一份手工/损坏的备份直接进来（`Services/BackupService.swift:479-496` 的 `toEntity(PersonaEntity)` 不做范围夹取）。
- **为什么错**：`abs(Int.min)` 溢出 trap → 首页渲染时就崩。
- **建议修法**：`let index = avatarSeed.magnitude % UInt(Self.palette.count)`，或在导入时把 `avatarSeed` 夹到安全范围。

### P2-11 「忘掉一条记忆」/「删掉一个人」不会清 `memory_versions`

- **位置**：`ios/MyFriendKit/Sources/MyFriendKit/Services/MemoryRepository.swift:400-404`（只删 `memories` + `memory_terms` + 向量）、`ios/MyFriend/App/AppEnvironment.swift:461-468`（删人格时没有 `memoryVersions`）。
- **为什么错**：`memory_versions` 里存着记忆的正文与 `beforeContent`（`Services/MemoryRepository.swift:461-490` 的漂移会写版本）。"忘掉"之后这些正文仍留在库里，既是数据库垃圾，也与"忘掉就是真删"的语义不符（`docs` 与 `MemoryConsolidator` 注释都这么写）；删人格后同样残留。
- **建议修法**：`MemoryRepository.delete` 里补 `stores.memoryVersions.delete(where: "memoryId = ?")`；`deletePersona` 里补一次按人格的批量清理。

### P2-12 清空类动作把错误全吞掉，仍然报告"都删掉了"

- **位置**：`ios/MyFriendKit/Sources/MyFriendKit/Services/DataReset.swift:170-189`（整段事务里每一步都是 `try?`）、`:154-207`（`clearAll()` 不抛错）；条目统计在删除**之前**取（`:155-165`），失败也照报。
- **为什么错**：只要有一张表删失败（锁/IO），用户看到的是"所有本地数据已删除（N 条…）"，但数据还在——对"删除全部数据"这种动作，静默半成功比报错更糟。
- **建议修法**：至少把失败的表收集成 `warnings` 返回并在界面上如实说明，或整体失败即整段 rollback 并抛错。

### P2-13 「删除全部本地数据」之后不会重新播种人格，要等下次启动

- **位置**：`ios/MyFriend/App/AppEnvironment.swift:294-302`（`seedIfNeeded()` 只在 `init` 里跑）、`:376-398`；清空入口 `Views/Settings/SettingsScreen.swift:692-700` / `Views/Backup/BackupScreen.swift:397-401`。
- **为什么错**：清空后首页是空的（`Views/Home/HomeView.swift:200-212` 的空状态让用户点「+」自建），重启 App 之后三个种子人格又出现——同一台设备上"出厂状态"出现了两种样子。
- **建议修法**：清空成功后调用一次 `seedIfNeeded()`（或把"是否已播种过"记成一个设置项，避免重启后又变）。

### P2-14 相册选图先把整张图读成 `Data` 再判大小

- **位置**：`ios/MyFriend/App/ImagePicking.swift:20-30`（`item.loadTransferable(type: Data.self)` 之后才进 `MediaStorage.saveImage`），大小上限判断在 `Support/MediaStorage.swift:353`。
- **为什么错**：一张 100MB 的全景/RAW 也会先被完整读进内存再被拒；`ImageEncodingPolicy.maxInputBytes = 20MB` 这道闸来得太晚（`Support/MediaStorage.swift:52-53`）。`loadTransferable(type: URL.self)` + `saveImage(at:)`（`:361-370`）已经有现成入口，用 `attributesOfItem` 先看大小即可。
- **建议修法**：优先 `loadTransferable(type: URL.self)`，先判文件大小再决定是否读像素。

## 我确认过但不构成缺陷的疑点

| 疑点 | 结论与证据 |
| --- | --- |
| `INSERT OR REPLACE` 会不会因为"隐式 DELETE + 外键级联"误删 `memory_terms` / `memory_vectors` / `memory_versions` | **不会**。`Data/Schema.swift:93-423` 的 DDL 里没有任何 `REFERENCES` / `FOREIGN KEY`，代码里也没有 `PRAGMA foreign_keys = ON`（`Data/SQLiteStore.swift:111-121` 只设了 `journal_mode` 与 `busy_timeout`），所以 REPLACE 不会级联。真正的风险是"整行替换导致丢失更新"，已单列为 P1-1 / P1-9。 |
| `LlmConcurrencyGate` 的等待者会不会双次 resume / 悬挂 | **不会双次 resume**。`expireWaiter`（`Net/LlmConcurrencyGate.swift:218-230`）与 `takeGrantableWaiterLocked`（`:233-246`）都在同一把锁内先 `firstIndex`/`remove` 再决定是否 resume；摘不到就返回。`installed == false`（`:162-165`）只取消定时器、不 resume，因为此时名额已经由 `release` 那条路径授予并 resume 过了。超时定时器的 `try? await Task.sleep` 被取消后会立刻调 `expireWaiter`，但那里同样摘不到 waiter。 |
| `AsyncMutex` 会不会漏名额 / 重入死锁 | **不会漏**。`withLock` 的 `defer release()` 在抛错时也执行（`Support/AsyncMutex.swift:57-61`）；`release` 在"有等待者"时不置 `busy = false`，所有权正确转交（`:44-54`）；三个调用点（`AgentLoop.tick`/`fireProactiveRule`、`MemoryConsolidator.consolidate`、`MemoryExtraction.extract`）都没有在持锁期间再进同一把锁。唯一问题是**没有超时**（见 P1-2、P2 排队的可用性影响）。 |
| SQLite 预处理语句会不会被缓存住造成内存增长 | **不会**。`SQLiteStatement` 每次 `prepare` 新建、`deinit` 里 `finalize`（`Data/SQLiteStore.swift:217-237`），没有语句缓存；`SQLiteRow` 强引用语句，不存在悬垂指针。 |
| 消息链接会不会把 `file://` / `javascript:` 塞进 WKWebView | **不会**。`Domain/LinkDetector.swift` 的约定与实现只放行 http/https（文件头注释与 `matchMarkdownLink`/`matchURL` 的白名单），`Views/Chat/ChatScreen.swift:744-747` 也只做 `URL(string:)` 校验后交给浏览器页。浏览器自身的导航白名单缺失另列 P2-8。 |
| API Key 会不会进备份 / 进数据库 | **不会**。`Services/BackupService.swift:674-687` 是白名单映射，`:206-208` 导出后还有 `containsSecretField` 自检；`Data/ApiKeyStore.swift:5-10` 说明 iOS 的 `apiKeyCipher` 列恒空，Key 只在 Keychain。风险只在 P1-5 的兜底路径。 |
| 用户点「停止」会不会丢掉已经吐出来的半句 | **不会**。`Chat/ChatService.swift:666-699` 有 `catch is CancellationError` 与 `Task.isCancelled` 两条兜底，会把 `shownText` 落成 `STOPPED` 消息（`allowEmpty: true`）；`Views/Chat/ChatViewModel.swift:328-343` 的 2 秒兜底只取消消费侧任务，不会阻止服务侧落库。 |
| 附件目录有没有排除 iCloud 备份 | **有**，`Support/MediaStorage.swift:322-333` 在 `init` 里设了 `isExcludedFromBackup = true`。缺陷只在 `deleteAll()` 之后丢失（P1-8）。 |
| 通知会不会在锁屏暴露聊天正文 | **不会**。`Services/BackgroundCatchUp.swift:156-177` 的 body 只有"给你发来一条消息/一张图片"，标题是人格名；测试也钉住了这一点。 |
| `swift test` 会写仓库里的 `fixtures/backup/ios-export-v2.json` | 是**设计如此**（`docs/IOS-PARITY.md:98` 写明 iOS 侧写盘供 Android 读），不是缺陷；只是提醒：跑完单测后 `fixtures/` 会有工作区改动，别误以为是手改。 |
| 工具痕迹标题是否仍是中文（`docs/I18N.md:122`、`docs/IOS-PARITY.md:176` 说未处理） | **文档过期**：`Chat/ToolProtocol.swift:513-527` 的标题已经全部走 `String(localized:)`，资源里也有对应 key。属于文档漂移，不是缺陷；除 P2-6 那两处漏网外，工具痕迹标题已本地化。 |

## 建议的修复顺序

1. **P0-1 事务串行化**（`SQLiteDatabase.inTransaction` 加锁 + `SAVEPOINT`/`autocommit` 判定）。这是唯一会静默丢数据的一条，改动小、收益最大，且后续所有并发修复都建立在"事务是可信的"之上。
2. **P1-1 会话行改定向 `UPDATE`** + **P1-2 补算去重**。这两条都会造成用户可见的数据错乱（预览倒退、未读错、摘要白压、双消息双通知），并且都在"每次回复"的热路径上。
3. **P1-5 Keychain 兜底 / P1-6 ATS**（安全闸，发布前必须解决，否则"Key 只在 Keychain""只允许 HTTPS"这两句对外承诺不成立）。
4. **P1-7 / P1-8 媒体失效路径**（清空不删文件、备份排除标记丢失）——都是"用户以为删干净了"的隐私问题，改动都是几行。
5. **P1-9 合并导入 + P1-10 发送失败回滚草稿**（数据完整性；建议补两条回归测试：同机合并自己备份后 `attachmentsJson` 不变、超长消息发送失败后 `draft` 不丢）。
6. **P1-3 前台心跳**（要么补上 30 秒循环，要么把文档改成现状；`IOS-PARITY.md` 与 `ARCHITECTURE.md` 都在描述一个不存在的能力，验收时会被当成回归）。
7. **P1-4 BGTask 上报语义 + P1-11 门控取消**（后台调度与取消传播，只有在真机上才看得见，建议同时补真机日志核对）。
8. 之后按 P2 顺序清理：P2-1/P2-2 内存与上限 → P2-6 文案 → P2-7 通知深链 → 其余（P2-10/P2-11/P2-12 属于边界健壮性，可随手带上）。

> 说明：本次审计**没有**跑 `xcodebuild`（结论全部来自源码阅读与 `swift test` 基线），也没有做模拟器运行时验证；P1-3、P1-4、P1-5、P2-7 四条建议在真机上按"触发条件"一栏复现一次再动手改。
