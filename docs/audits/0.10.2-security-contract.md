## 安全问题（P0/P1/P2）

### P1-0（影响等同 P0）备份导入可劫持既有 API 配置（保持本机密钥）→ 密钥与聊天内容外泄 / 明文降级

**位置（两端同构）**

- Android：`app/src/main/java/com/yap/app/data/repo/BackupRepository.kt:308-313`（导入直接写 DAO，不经 `ApiConfigRepository.save` 的任何校验），
  `app/src/main/java/com/yap/app/domain/BackupCodec.kt:919-936`（`mergeInto` 无条件覆盖 `baseUrl` 与 `allowInsecureHttp`），
  `BackupCodec.kt:941-960`（`toNewEntity` 同样接受备份里的 `allowInsecureHttp`）。
- iOS：`ios/YapKit/Sources/YapKit/Services/BackupService.swift:366-369`（导入循环）、
  `BackupService.swift:693-710`（`mergeInto`：`merged.baseUrl = imported.baseUrl.isEmpty ? existing.baseUrl : imported.baseUrl`、
  `merged.allowInsecureHttp = imported.allowInsecureHttp`）、`BackupService.swift:715-735`（`toNewEntity`）。

**触发条件**（用户动作 + 一份可控 JSON，两个平台都一样）

1. 攻击者知道受害者设备上**某条 API 配置的 id**（UUID）。这不是秘密级数据：任何一次导出的备份 JSON 都明文带着它，
   所以"用户曾经分享过备份 / 人格包"或"受害者先导入过攻击者的备份"之后，这个 id 就是已知的；
   攻击者据此拼一份备份，把该配置的 `baseUrl` 改成自己控制的主机（或 `http://` 明文地址）、
   `allowInsecureHttp` 改成 `true`；
2. 用户「接他回来」→ 合并导入（默认就是合并）。`mergeInto` 只覆盖"非敏感字段"，**本机 `apiKeyCipher` /
   Keychain 里的 Key 被原样保留**；
3. 下一次聊天：`Authorization: Bearer <用户真实 Key>` + 全部上下文消息被发到攻击者主机。

**影响**（满足上述前提时）：API Key 泄露（可直接盗刷）、全部聊天/记忆/人格提示词外泄、或在不被用户察觉的情况下把请求降级为明文 HTTP
（`allowInsecureHttp` 是"每配置一次显式同意"的开关，导入把它静默打开了）。同一路径还能写入 `temperature=1e9`、
超长 `model` 等绕过 `ApiConfigRepository.save` 校验（`ApiConfigRepository.kt:66-121`）的值。

**建议修法**

- 导入时**不覆盖** `baseUrl` / `allowInsecureHttp` / `webToolsBaseUrl`（这些是"这台设备对这个服务商的信任决定"，
  不是可迁移内容）；确实要改地址时走"用户手动编辑 + 重新输入 Key"。
- 若坚持迁移地址：只接受与现有 `baseUrl` **同源**（scheme+host+port 相同，或同为官方 host）的备份值；
  `allowInsecureHttp=true` 必须要求用户当场再确认一次，并在导入摘要里列出"地址被改"的配置。
- 导入完成后重新跑一遍 `ApiConfigRepository` 的校验（scheme / 参数范围 / header 形状）。

### P1-1 iOS：Keychain 失败时把明文 Key 写进 `UserDefaults`，Release 也走这条路

**位置**：`ios/YetAnotherPal/App/ResilientKeychain.swift:20-31`（`set` 的 catch 分支直接
`UserDefaults.standard.set(value, forKey:)`，**没有任何 `#if DEBUG` / `targetEnvironment(simulator)` 限定**）、
`:33-40`（`get` 读回）、`:53-55`（键名前缀 `debug.keychain-fallback.`）；
装配在 `ios/YetAnotherPal/App/AppEnvironment.swift:86`（`ApiKeyStore(backend: ResilientKeychain())`，正式构建同样使用）。

与文档冲突：`docs/IOS-PARITY.md:105-109` 写的是"**真机签名构建走 Keychain；模拟器上失败时**把 Key 临时放进 UserDefaults"。
实际代码没有"是不是模拟器"的判断，失败即落盘。

**触发条件**：任何 `SecItemAdd`/`SecItemDelete` 失败，例如
（a）未签名构建（文档里的场景）；（b）进程在设备首次解锁前被后台任务拉起时去写 Key；
（c）Keychain 数据损坏 / 迁移异常的设备。之后只要用户再保存一次 Key，明文就留在 `UserDefaults`。

**影响**：API Key 以明文形式落在 `Library/Preferences/com.yap.app.ios.plist`，该文件**默认会进 iCloud/iTunes 备份**，
与 `ApiKeyStore.swift:3-10`、`Keychain.swift:14-15` 反复强调的"Key 不进备份是硬规矩"直接矛盾；
也高于 Android 侧（Keystore 不可导出，备份里只有无用的密文）。

**建议修法**：兜底只在 `#if DEBUG && targetEnvironment(simulator)` 生效；Release 下写失败要向上抛，让设置页明确提示
"这台设备无法安全保存密钥"；启动时清掉所有 `debug.keychain-fallback.` 前缀的历史条目。

### P1-2 两端都是「系统层允许明文 HTTP」，HTTPS 只剩 App 内一道闸

**位置**

- Android：`app/src/main/AndroidManifest.xml:26` `android:usesCleartextTraffic="true"`，且没有 `networkSecurityConfig`
  —— 全 App、全域名允许明文；唯一拦截是 `app/src/main/java/com/yap/app/network/NetworkGuard.kt:14-24`。
- iOS：`ios/Config/Info.plist:73-80` `NSAllowsArbitraryLoads=true`（+ `NSAllowsLocalNetworking`），
  这是**发布配置**（`ios/YetAnotherPal.xcodeproj/project.pbxproj:192-193,214-215` 的 `INFOPLIST_FILE = Config/Info.plist`，
  Debug/Release 共用）。注释自己写了"正式发布前应改成 HTTPS（或只留域例外）"，但代码现状没有改。

**触发条件**：任何让 App 发出 `http://` 请求的路径 —— 用户手开"允许不安全 HTTP"、或 `P1-0` 的备份导入把它打开。

**影响**：`NetworkGuard` 是唯一防线；一旦它被绕过（`P1-0` 就是这样），系统层不会兜底，明文请求照样发出，
API Key 随 `Authorization` 头裸奔。ATS 关闭同时放开 TLS 版本/套件的最低要求，削弱了"Key 在传输中安全"的保证。
两端行为一致，但与"默认只允许 HTTPS"的产品承诺不一致。

**建议修法**：Android 用 `networkSecurityConfig`（release 只允许 https，本地调试域放 `debug-overrides` 或独立的 debug manifest）；
iOS 移除 `NSAllowsArbitraryLoads`，只保留 `NSExceptionDomains` 针对本地调试域名（如 `192.168.*`、`localhost`），
并把"允许不安全 HTTP"开关限制为 debug 构建可用。

### P2-1 自定义 Headers 未过滤 `Host`（Android 已核实会被原样发出）

**位置**：`app/src/main/java/com/yap/app/network/OpenAiAdapter.kt:340-360`（只跳过 `Content-Type`，`Authorization` 只是记录"用户自定义过"）、
写入前唯一的校验是 `app/src/main/java/com/yap/app/data/repo/ApiConfigRepository.kt:210-221`（只要求 key 非空、value 是字符串）；
iOS 同构：`ios/YapKit/Sources/YapKit/Net/OpenAICompatibleClient.swift:634-659`、`parseHeaders` `:661-676`。

**核实**：反编译 OkHttp 4.12 `BridgeInterceptor` 确认 —— `Content-Length` 会被框架覆盖、`Transfer-Encoding` 被强制，
但 **`Host` 只在缺失时才补**（`getRequest().header("Host")` 非 null 就保留用户值）。CRLF 注入由 `Headers` 的值校验拦住。

**影响**：可以把请求路由到同一 IP:端口上的另一个虚拟主机（对反代/网关场景有意义）；不能改变 TCP 目标，也不影响 TLS 证书校验，
所以够不上 P1。iOS 的 `URLRequest.setValue("Host")` 是否被 URLSession 覆盖**本轮未验证**。

**建议修法**：两端共用黑名单 `Host` / `Content-Length` / `Transfer-Encoding` / `Connection` / `Expect` / `Proxy-*`，
命中时保存配置就报错。

### P2-2 附件文件的"只删自己目录"守卫只给了头像，没给附件

**位置**：Android `app/src/main/java/com/yap/app/util/MediaStorage.kt:174-176`（`deleteFiles` 对任意 `file://` 直接 `delete()`，

### P2-3 备份导入没有大小上限，整份读进内存

**位置**：Android `app/src/main/java/com/yap/app/ui/screens/settings/BackupSection.kt:197-201`
（`openInputStream(uri)?.bufferedReader()?.use { it.readText() }`）；iOS `ios/YetAnotherPal/Views/Backup/BackupScreen.swift:333`
（`String(contentsOf: url, encoding: .utf8)`）。之后才是 `BackupCodec.decode`。

**触发条件**：用户选中一个超大（几百 MB～GB）的"备份"文件。

**影响**：两平台都会先把整份文件读成字符串，再解析：低内存设备 OOM/被系统杀进程，且 OOM 发生在 UI 附近
（Android 在 IO 线程读、但字符串仍占堆）。深度嵌套已验证不会打挂解析器（见"验证过但不成立"）。

**建议修法**：读之前用 `contentResolver.openAssetFileDescriptor` / `FileHandle` 查 size，超过上限（如 64 MB）直接拒绝并给文案；
解析侧同样限长。

### P2-4 两端"整机备份包含什么"的策略相反，且 iOS 的 Keychain 条目会随加密备份走

**位置**：Android `app/src/main/AndroidManifest.xml:17-19`（`allowBackup=false` + `fullBackupContent=false`）+
`app/src/main/res/xml/data_extraction_rules.xml`（cloud-backup / device-transfer 全排除）——**系统备份里什么都没有**。
iOS：只有附件目录被排除（`ios/YapKit/Sources/YapKit/Support/MediaStorage.swift:326-332`，
`isExcludedFromBackup = true`），而数据库在 `Application Support/yap.db`
（`ios/YetAnotherPal/App/AppEnvironment.swift:584-593`）**没有被排除**，`UserDefaults`（`SettingsStore.swift:167-186`）也没有。
Keychain 条目的可访问性是 `kSecAttrAccessibleAfterFirstUnlock`（`ios/YapKit/Sources/YapKit/Support/Keychain.swift:58`），
不是 `…ThisDeviceOnly`，按 Apple 文档会包含在加密备份里。

**影响**：Android 换机恢复后"什么都没有"（用户必须自己导入备份 JSON，这是设计选择）；
iOS 换机恢复会把全部聊天/记忆/人格/设置从 iCloud 备份带回来，Keychain 里的 API Key 也会跟着回来。
两端对"我的数据会进云端备份吗"给出的事实上不同答案，文档里没有说明。

**建议修法**：明确写进隐私说明；若要一致，iOS 对 db 设置 `isExcludedFromBackup`，Keychain 改 `AfterFirstUnlockThisDeviceOnly`。

### P2-5 备份里带设备绝对路径（`avatarUri`）

### P2-6 Android 的 `hasKey` 只看密文非空，Key 丢失后会"假装已配置"

**位置**：`app/src/main/java/com/yap/app/data/secure/SecretCipher.kt:47`（`hasKey(encoded) = !encoded.isNullOrBlank()`）、
`app/src/main/java/com/yap/app/data/repo/ApiConfigRepository.kt:52,59`（解密失败返回 null）；UI 的"已保存"只看密文是否为空：`app/src/main/java/com/yap/app/ui/screens/apiconfig/ApiListScreen.kt:279-283`。

**影响**：Keystore 密钥被系统清掉/迁移异常后，Android 用户看到"Key 已保存"，发消息却只会得到 401；
两端对同一状态的显示不同。属于一致性与可诊断性问题（非泄漏）。

**建议修法**：`hasKey` 改为"能解密且非空"（缓存一次解密结果即可），失败时在设置页给出"密钥需要重新输入"。

### P1-4 数据库 schema：Room v10 与 iOS `user_version=10` 并非逐字一致

对照 `app/schemas/com.yap.app.data.local.YapDatabase/10.json` 与
`ios/YapKit/Sources/YapKit/Data/Schema.swift`（脚本逐表/逐列/逐索引比对）：

`NOT NULL DEFAULT` 回填（可先 UPDATE 再重建表）。

### P1-5 备份格式：iOS `BackupSession` 多写 6 个 sync 字段，违反"字段名逐字相同"

**位置**：`ios/YapKit/Sources/YapKit/Backup/BackupModels.swift:328-333`（字段）、`:405-407`（`CodingKeys` 含

**建议修法**：从 iOS `BackupSession` 结构与 `toBackupSession` 删除这 6 个字段（解码侧保留忽略即可）；

### P2-10 SSE 单行上限两端不同（Android 8MB / iOS 1MB）

**位置**：`app/src/main/java/com/yap/app/network/SseLines.kt:19-40`（8MB，超限抛 `ResponseTooLong` 并中止流）；
`ios/YapKit/Sources/YapKit/Net/SSE.swift:35-61`（1MB，超限时把缓冲区当成**一整行**照常产出事件，不中止）。

**影响**：同一段异常/恶意响应，Android 先中止、iOS 会继续把 1MB 的"一行"交给上层 JSON 解析（解析失败 → 空 chunk）。

**建议修法**：把"单行上限 + 超限行为"写进 `spec/`（或至少写进 `IOS-PARITY` 平台差异表），并让两端阈值一致。

## 验证过但不成立

下面是本轮**专门去查、结论是不构成问题**的点：

1. **`web_fetch` 能抓 localhost / 内网 / `file://`（设备侧 SSRF）**：不成立。两端都**不建立**到目标 URL 的连接，
   而是把 URL 作为 JSON 字段 POST 给 `{base}/v1/tools/fetch`，抓取发生在 DeepSeek 服务端
   （Android `DeepSeekWebTools.kt:88-105,162-189`、iOS `WebToolsClient.swift:241-307`）。设备侧没有可被模型利用的 SSRF 面。
   （Android 缺 scheme 校验已单列 P2-11。）
2. **密钥进备份**：结构上不可能。`BackupApiConfig` 白名单只有 15 个非敏感字段
   （Android `BackupCodec.kt:296-327,895-916`；iOS `BackupModels.swift` 的 `BackupApiConfig` + `BackupCodec.swift:29-42`），
   导出前还有 `containsSecretField` 自检（Android `BackupCodec.kt:424-432`、iOS `BackupCodec.swift:32-42`，同一张标记表）。
   两端 fixture 测试都断言导出里没有 `apiKeyCipher/apiKey/Authorization/customHeadersJson`。
3. **`containsSecretField` 会因人话里出现 `"apiKey"` 误报**：不成立。JSON 编码会把内容里的引号转义成 `\"`，
   文本中不会出现 `"apiKey"`（引号+反斜杠）这个精确子串；只有真实的字段名会命中。
4. **人格导出泄漏密钥**：不成立。`PersonaRepository.exportPersonas`（`app/src/main/java/com/yap/app/data/repo/PersonaRepository.kt:364-384`）
   只写 name/description/prompt/category/content-URI 头像/seed/version，没有 Key 或自定义 Header。
5. **日志泄漏消息正文 / 记忆 / 人格提示词**：不成立。Android 全仓只有 2 处 `Log.*`
   （`network/LlmGatekeeper.kt:35` 并发位超时、`data/repo/WebSearchScorer.kt:72` 打分明细），都不含正文；
   iOS 有 28 处 `DebugSeeding.log`，全是计数/ID/状态（人工逐条看过），且整个 `DebugSeeding` 包在 `#if DEBUG`
   （`ios/YetAnotherPal/App/DebugSeeding.swift:18`），Release 里不存在；全仓无 `print`/`NSLog`。`debug.log` 只写 `Documents`，
   也只在 DEBUG 构建产生。
6. **遥测 / 崩溃上报把内容带走**：不成立。两端都没有第三方 SDK：Android 依赖里没有 firebase/crashlytics/sentry
   （`app/build.gradle.kts:106-152`），iOS 无外部 SPM 依赖（只用 Foundation/SwiftUI/WebKit/Security）。零遥测。
7. **超深嵌套的备份 JSON 打挂解析器**：不成立。实测把 100000 层嵌套数组塞进 `personas` 交给 Android `BackupCodec.decode`
   → 返回 `Failure(InvalidJson)`（`runCatching` 兜住，没有崩溃/StackOverflow 逃逸）；1000 层则被当作一条坏记录丢弃并给出
   `DroppedRows` 警告。iOS 用 `JSONDecoder`（`Support/JSONValue.swift:70-80`），有内建深度上限，超限返回 nil → 中文"读不出来"。
8. **Android WebView 可直接读本机文件 / 有 JS 桥**：不成立。`ui/screens/browser/InAppBrowserScreen.kt:378-392` 关了
   `allowFileAccess` / `allowContentAccess` / `allowFileAccessFromFileURLs` / `allowUniversalAccessFromFileURLs`，
   没有 `addJavascriptInterface`，`setSupportMultipleWindows(false)`、`onCreateWindow` 返回 false；
   外部 scheme 交系统（`InAppBrowserScreen.kt:295-305`）。iOS `WKWebView` 默认不允许 file:// 访问、无 JS bridge。
   （唯一值得加固的是：Android 会把任意 scheme 交给系统 Intent，`intent://...` 可以拉起别的组件——因未做动态验证，放进下方"未验证"清单。）
9. **聊天里的链接能引导 App 打开 `javascript:` / `file:` / `intent:`**：不成立。两端 `LinkDetector` 只放行 http(s)
   （Kotlin `domain/LinkDetector.kt:115-135`、Swift `Domain/LinkDetector.swift:117-126`），InAppBrowser 入口再收敛一次
   （Android `InAppBrowserScreen.kt:83-86`）。
10. **iOS 备份不含"附件图片"这件事没做全（`isExcludedFromBackup` 没覆盖全部附件目录）**：不成立。iOS 只有一个附件目录
    `Application Support/attachments`（头像也在这里，按 `kind` 前缀命名），`MediaStorage.init` 对其设置
    `isExcludedFromBackup = true`（`ios/YapKit/Sources/YapKit/Support/MediaStorage.swift:322-333`）。
    Android 侧因为 `allowBackup=false`，整个应用目录都不进系统备份。
11. **两端 DND / `readAt` 语义不一致**：不成立。判定逻辑由同一批 spec 用例钉住
    （`spec/agent-core/cases/sleep-decision.json`），`marksRead` 的落库位置两端一致
    （Android `data/repo/ChatRepository.kt:366-373`、iOS `Chat/ChatService.swift:443-449,467`）。
    唯一实现差异：iOS 统计"最近 N 分钟几条用户消息"是按 persona（`ChatService.swift:438-441`），Android 按 session
    （`ChatRepository.kt:1021-1023`）——因为两端都强制"一人一段"（唯一索引），两者等价。
12. **`defer_reply` 夹取 / 主动上限映射 / 用量类目两端漂移**：不成立。`ToolArgClamp` 的 5–720 / 默认 45 / 窗口 +30
    由 `spec/agent-core/cases/defer-plan.json` 两端同时断言；`ProactiveLevel` 的 dailyCap/weights/description 由
    `proactive-cap.json` 钉住（`ProactiveLevel.swift:30-56` 与 `ProactiveLevel.kt:21-60` 数值与文案逐字一致）；
    `UsageKind` 9 个常量与 `displayOrder` 两端完全相同（`app/src/main/java/com/yap/app/domain/ApiCost.kt:44-70`、
    `ios/YapKit/Sources/YapKit/Net/UsageCost.swift:47-79`）。
13. **Android 把 API Key 明文写进 DataStore**：不成立。DataStore 的键里没有任何密钥字段
    （`data/prefs/SettingsRepository.kt:33-48`），Key 只以 Keystore 密文存在 `api_configs.apiKeyCipher`
