**最该先修的 3 条**

1. **P1-2 备份导入的「空包闸」只判断顶层计数，不校验跨表引用**：一份 `messages`/`memories` 非空、但
   `sessions`/`personas` 缺失或不一致的备份能通过预览与仓库闸门，`REPLACE` 会先清空本机、再把这些落不下去的
   行丢掉。用户得到的是「本机数据没了、备份也没接回来」。这是 0.11.0 新加的 `BACKUP_EMPTY` 闸没有覆盖到的
   数据丢失路径（后果接近 P0，但需要用户确认替换一份结构不完整的外部文件）。
2. **P1-1 从检索结果跳进有界窗口后，发送/重新生成的消息不在窗口里，`hasMoreNewer` 又只在定位时算一次**：
   用户打完字发出去，列表里看不到自己刚发的那条；回复也落在窗口外；某些定位结果下连「更新的消息」入口都没有。
   这是 0.11.0 新功能（`MessageJump` 有界窗口）与既有发送路径的生命周期脱节。
3. **P1-4 删除路径在 Room 事务里删媒体文件**：备份替换/删人格在事务内就把聊天图片与头像文件删掉；一旦事务
   回滚（约束冲突、磁盘满、后续 `markDefault` 失败），数据库里的消息/人格还在，文件却已经没了，回滚不再是
   「什么都没变」。这与 `DataEraser` 自己的 KDoc「表删除在事务里、文件删除在事务外」直接矛盾。

## P1

### P1-1 定位到旧消息后的有界窗口不感知新消息：发送/重新生成不可见，`hasMoreNewer` 永久为 false

- **位置**：
  - `app/src/main/java/com/myfriend/app/ui/screens/chat/ChatViewModel.kt:189`（`jumpWindow`）、`:198-214`
    （`messageFlow`：窗口非空时只观察 `observeWindow(sessionId, start, rows)`）、`:340-355`
    （`startJumpToTarget` 写入窗口与游标）、`:367-371`（只有 `showLatest()` 会清窗口）、
    `:291`（把 `paging.hasMoreNewer` 直接交给界面）、`:486-526`（`send()` 不碰窗口）、
    `:597-630`（`regenerate()` / `editUserMessage()` 同样不碰窗口）
  - `agentcore/src/main/kotlin/com/myfriend/app/domain/MessagePaging.kt:76-84`（`onJumped` 只在这时算一次
    `hasMoreNewer`，`onLatest` 才复位）
  - `app/src/main/java/com/myfriend/app/ui/screens/chat/ChatScreen.kt:1007-1016`（「更新的消息」入口只在
    `state.hasMoreNewer` 为真时渲染）
- **触发**：搜索命中一条旧消息 → 点进会话（`MessageJump` 装载一个有界窗口）→ 直接输入并发送；或在这个窗口里
  点「重新生成」/编辑消息。更严重的一种：定位窗口正好覆盖到会话末尾（`plan.hasMoreNewer == false`，例如
  200 条会话跳到第 100 条，窗口是 40..199）后，来一条新消息或自己发一条。
- **为什么错**：窗口观察是 `LIMIT rows` 的固定区间（`ChatRepository.observeMessagesWindow` →
  `MessageDao.observeWindow`），新消息的 `createdAt` 在区间之外，Room 重跑也只回原来 160 条。`send()` 只写库 +
  `startGeneration`，不调用 `showLatest()`，也不清 `sinceCursor/jumpWindow`，所以自己刚发的用户消息不在
  `state.messages` 里；随后助手回复同样在窗口外。`hasMoreNewer` 由 `MessageJump.plan` 在定位那一刻算一次，
  之后既没有随消息表重算、也没有在 `loadOlder()` 里更新；当它本来就是 false 时，界面连「更新的消息」这一行
  都没有，用户只能退出会话再进——用户感知是「发出去的话消失了、他不理我」。**实测**（javac 直接调
  `agentcore/build/libs/agentcore.jar`）：`MessageJump.plan(total=200, beforeTarget=100, pageSize=60)` 返回
  `windowRows=160`、`hasMoreNewer=false`，即窗口 40..199、目标之外的更新消息一条都不会自动出现。
- **建议修法**：`send()` / `regenerate()` / `editUserMessage()` 在写库前先 `showLatest()`（或至少在
  `jumpWindow != null` 时清窗口、恢复实时观察）；同时让 `pagingState.hasMoreNewer` 在窗口数据变化时按
  「窗口末尾 < 会话最新一条」重算，而不是只信定位时的计划。

### P1-2 备份导入的「空包闸」不校验跨表引用：结构不完整的备份能通过并清空本机

- **位置**：
  - `app/src/main/java/com/myfriend/app/data/repo/BackupRepository.kt:181-185`（新增的空包闸只检查
    `personas/memories/sessions/messages/presets/proactiveRules` 六个顶层列表是否全空）
  - `:240-274`（`latestSessions` 只保留每个人格最新一段；`messages` 用 `sessionIdMap.values` 过滤，落不下去的
    只 `skipped++`）
  - `:291-305`（`REPLACE` 在同一个事务里先 `dataEraser.replaceForBackupInsideTransaction` 清空本机，再写回）
  - `app/src/main/java/com/myfriend/app/domain/BackupCodec.kt:369-370`（`isEmpty` 只看 4 个计数）、
    `:463-475`（各段缺失时 `decodeList` 直接返回空列表，不报错、也不产生会阻断导入的 warning）
  - `app/src/main/java/com/myfriend/app/ui/screens/settings/BackupSection.kt:309-320`（`preview.isEmpty == false`
    就给出「合并 / 替换」两个按钮，替换是红色按钮）
- **触发**：选一份能解析、但结构不完整的备份文件，例如
  `{"format":"myfriend.backup","formatVersion":2,"messages":[{...}]}`（没有 `sessions`/`personas`），或
  `sessions` 存在但对应 `personas` 被删掉/改名，或只有 `memories` 没有 `personas`。预览里
  `messages=1`（或 `memories=N`），`isEmpty` 为 false，界面显示「1 句话」，没有警告；用户点「替换」。
- **为什么错**：仓库层的空包闸是按「任意一段非空」判的，不是按「这份备份能落成什么」判的。`REPLACE` 分支
  已经先把 `messages/chat_sessions/memories/personas/...` 清空（`ErasurePlan.BACKUP_REPLACE`），随后：
  `sessions` 为空 → `sessionIdMap` 为空 → 所有 `messages` 被 `filter` 掉（只留下一条 `skipped` warning）；
  `personas` 为空 → `personaDao.insertAll(空)`，但本机人格已被删；只有 `memories` 时同理，会插入一批
  `personaId` 指向不存在人格的孤儿记忆。结果是「本机全没了、备份也没接回来」（或只剩不可见/半残的行），
  而空包闸的本意正是防止这种「替换成空」。0.10.2 报告里「拿一份读不懂的备份点替换 → 全清」被 UI 挡住；
  现在「读得懂但结构不完整」这条又漏了。
- **建议修法**：在进入 `database.withTransaction`（清空）之前，先算一遍**可落库集合**：要求
  `personas` 非空、`sessions` 的 `personaId` 都能在 `personas` 中找到、`messages` 的 `sessionId` 都能在
  `latestSessions` 中找到；任何一项不满足就 `BackupImportException`（或在 REPLACE 时降级成拒绝），绝不先清后弃。

### P1-3 备份导入/导出的 JSON 处理仍在主线程：64MB 上限让 ANR 变得可达

- **位置**：
  - 导入：`app/src/main/java/com/myfriend/app/ui/screens/settings/SettingsViewModel.kt:233-245`
    （`openBackup` 在 `viewModelScope.launch` 里调 `backupRepository.preview`）、`:256-269`（`importBackup` 同样）、
    `app/src/main/java/com/myfriend/app/data/repo/BackupRepository.kt:198`（`preview` 是普通函数）、
    `:205-213`（`importJson` 在调用方上下文里 `BackupCodec.decode`）、
    `app/src/main/java/com/myfriend/app/domain/BackupCodec.kt:437-446`（`parseToJsonElement` + 逐段反序列化）
  - 导入的写库前映射：`BackupRepository.kt:229-293`（`personas.map`、`messages.map`、`filter` 都在
    `database.withTransaction` 之前，即调用方 Main）
  - 导出：`SettingsViewModel.kt:223-232`（`buildBackupJson` 只包了 `runCatching`，没有 `withContext(IO)`）、
    `BackupRepository.kt:137-190`（`sessions.flatMap { messageDao.getBySession(...) }` 的 N+1 查询、全部
    `map` 与 `BackupCodec.encode` 都在调用方上下文）
  - 对比：同一入口的**读文件**已经切 IO（`BackupSection.kt:204-213`），聊天导出也已切 IO
    （`ChatRepository.kt:1124-1190`）
- **触发**：导入一份几 MB～64MB 的备份（0.11.0 明确允许到 64MB），或导出有几千上万条消息的库。
- **为什么错**：读取被挪到了 `Dispatchers.IO`，但解析、DOM 构造、逐段反序列化、`BackupBundle` 映射都在
  `viewModelScope`（Main）上。几 MB 的 JSON 解析已经是几十到几百毫秒；64MB 的输入在 Main 上是秒级，直接
  ANR。导出侧还把整个字符串 + DOM 都留在主线程，和已经修好的聊天导出（`exportSession` / `exportAllChatsTo`
  都 `withContext(Dispatchers.IO)`、后者分批写）不对称。`BoundedTextRead` 只保证「不把整份文件读进内存」，
  并不保证解析不在主线程。
- **建议修法**：`SettingsViewModel` 的两个入口统一
  `withContext(Dispatchers.IO) { backupRepository.preview/importJson(...) }`；`BackupRepository.exportJson`
  内部 `withContext(Dispatchers.IO)`（更好的做法是像 `ExportJsonStream` 一样分批编码，避免整份 String +
  DOM 峰值）。

### P1-4 删除路径在数据库事务内删媒体文件：事务回滚后库引用已删文件

- **位置**：
  - `agentcore/src/main/kotlin/com/myfriend/app/domain/DataErasure.kt:204-205`（KDoc 明确写「表删除在一个事务里；
    文件删除在事务之外」）、`:232-235`（`deletePersona` 用 `store.inTransaction { deletePersonaInsideTransaction }`）、
    `:247-248` + `:265-269`（`replaceForBackupInsideTransaction` / `deletePersonaInsideTransaction` 在调用方事务里）、
    `:271-276`（`_replaceForBackup` 在事务内 `clearChatImages` + `clearUnreferencedAvatars`）、
    `:278-287`（`_deletePersona` 在事务内 `deleteChatImages` + `deleteAvatar`）
  - `app/src/main/java/com/myfriend/app/data/repo/PersonaRepository.kt:226-239`（`database.withTransaction` 里
    `dataEraser.deletePersonaInsideTransaction`，之后还要 `markDefault`）
  - `app/src/main/java/com/myfriend/app/data/repo/BackupRepository.kt:291-305`（备份替换的清空 + 写回在同一个
    `database.withTransaction` 里，清空内部就删文件）
- **触发**：备份「替换」导入进行到一半时事务失败（约束冲突、磁盘满、进程被杀前的回滚等）；或删人格事务里
  `personaDao.markDefault` 抛错。文件删除先执行且不可回滚，DB 事务随后回滚。
- **为什么错**：`MediaStorage.clearChatImages/clearUnreferencedAvatars/deleteChatImages/deleteAvatar` 是
  **不可回滚的文件系统副作用**。备份替换失败时，`messages`/`personas` 会随事务回滚回来，但它们引用的
  `files/media/chat-*.jpg`、`files/avatars/avatar-*.jpg` 已经被删；用户看到的是「导入失败，本机没变」，
  实际上一批聊天图片/头像已经永久丢失（`clearUnreferencedAvatars` 还会把不在 keep 集合里的旧头像一起删）。
  删人格失败时同理。这也让 `DataErasureContractTest` 的「失败会整体失败」只覆盖了表、没有覆盖文件。
- **建议修法**：事务内只收集待删文件路径（`attachmentsOfPersona`/`avatarUri`/chat 图片清单），事务提交后再
  执行文件删除；备份替换把 `clearChatImages/clearUnreferencedAvatars` 移到 `withTransaction` 之后（保留
  `keepAvatarUris` 在提交后计算）。失败重试时允许「文件暂时是孤儿」，不要让「DB 回滚 + 文件已删」出现。

## P2

### P2-1 `ProactiveRepository` 自算消息时间戳，没走 `MessageOrder`（P2-7 的第三条写路径）

- **位置**：`app/src/main/java/com/myfriend/app/data/repo/ProactiveRepository.kt:333-341`
  （`val created = System.currentTimeMillis(); val stamp = if (created <= now) now + 1 else created`）、
  `:347-351`（`lastMessageAt = stamp`）；对比 `ChatRepository.kt:1407-1410` 与 `AgentLoop.kt:429-433` 都走
  `MessageOrder.nextTimestamp(latestInSession(...))`。
- **触发**：主动规则到点发消息，同时用户刚发出一条消息（同一毫秒）；或 `MessageOrder` 之前把最新一条推到
  `now + k`（同一毫秒连写）后，主动消息用墙钟值写入。
- **为什么错**：这里没有读会话里的最新 `createdAt`，`stamp` 可能等于甚至小于最新一条用户消息。排序是
  `(createdAt, id)`，`id` 是随机 UUID，所以同一毫秒时助手消息可能排在用户消息**前面**；`lastMessageAt` 也可能
  比现有值小，会话列表按它排序会把这段对话往后挤。这与 `MessageOrder` KDoc「会话内时间戳严格递增、只有一份
  实现」不一致，也是 0.10.2 P2-7 的漏项：两条聊天路径修了，主动规则路径没修。
- **建议修法**：改成 `MessageOrder.nextTimestamp(messageDao.latestInSession(session.id)?.createdAt,
  System.currentTimeMillis())`，并补一条「主动消息与用户消息同毫秒」的纯逻辑/接线测试。

### P2-2 「清空全部聊天与记忆」不撤通知、不清 `openSessionTracker`（`wipeAllData` 都做了）

- **位置**：`ChatRepository.kt:1211-1213`（`clearAllChatData` 只调 `dataEraser.clearChatsAndMemories()`）对比

### P2-3 备份「替换」不取消在跑的生成、不 bump 世代：同设备备份可能把半截回复写进刚恢复的会话

- **位置**：`BackupRepository.kt:205-213`（`importJson` 解码后直接 `importBundle`）、`:291-305`（REPLACE 清空 +
  写回；没有 `sessionGeneration` / `cancelGeneration`）；对比 `ChatRepository.kt:875-884`（`clearContext`）与

### P2-7 远程实现缺少网络加固：跟随重定向、响应体无上限、回退不可观测

- **位置**：`app/src/main/java/com/myfriend/app/core/AgentCoreClient.kt:102-107`（`httpClient.newBuilder()` 没有

### P2-8 64MB 上限不等于不 OOM：BAOS + UTF-16 String + Json DOM 的峰值仍是上限的 2–3 倍

- **位置**：`agentcore/src/main/kotlin/com/myfriend/app/domain/BackupLimits.kt:21-24`
  （`MAX_BACKUP_BYTES = 64MB`、`MAX_BACKUP_CHARS = 64M`）、`BoundedTextRead.kt:25-36`
  （`ByteArrayOutputStream` 按块增长到上限，再 `toString(UTF_8)`）、`BackupCodec.kt:437-446`
  （`readJson.parseToJsonElement(raw)` 再逐段 `decodeFromJsonElement`）。
- **触发**：用户选中一份接近 64MB 的合法/半合法 JSON（0.11.0 明确允许），中端机（heap 192–256MB）。
- **为什么错**：64MB 字节的 BAOS 内部会按倍增扩容（峰值可到 128MB 的瞬时副本），`toString(UTF_8)` 在 Android
  上是 UTF-16 String（64MB ASCII → 约 128MB），`parseToJsonElement` 再建一棵 DOM（通常再 2–3 倍）。这三层
  叠加时，64MB 的「上限」并不能阻止 OOM；`BoundedTextRead` 的 KDoc「堆峰值只有上限那么多」只对字节数组成立。
  且导出侧没有对称上限（见 P1-3），可能出现「导出的备份自己导不回来」。
- **建议修法**：把导入上限降到与设备堆相称的量级（例如 8–16MB，或按 `ActivityManager.memoryClass` 动态算），
  并/或改成流式 JSON 解析；导出侧也用同一个常量并分批（`ExportJsonStream` 已有基础设施）。

### P2-10 API 26–27 上「长边 ≤1024」没有落实：`BitmapFactory` 粗采样后不再缩放到目标尺寸

- **位置**：`app/src/main/java/com/myfriend/app/util/MediaStorage.kt:361-384`（`decodeForContext` 的 API<28 分支：
  `while (longest / sample > targetEdge * 2) sample *= 2` 后直接 `decodeFile`，没有 `createScaledBitmap`）；
  `agentcore/src/main/kotlin/com/myfriend/app/domain/ImageContextBudget.kt:37-38`（`TARGET_EDGE_PX = 1024` 与
  「长边压到 1024」的承诺）。
- **触发**：Android 8.0/8.1（minSdk 26/27）上发送长边 4000px 的截图/照片。

  前按 `TARGET_EDGE_PX` 缩），并把「目标尺寸计算」抽成纯函数加一条 JVM 单测。

  第三方抓取服务。抓取发生在服务端，所以不是设备侧 SSRF（这一点与 0.10.2 的定性一致），但这是一道名义上
  「拒绝内网字面量」、实际只挡了常见写法的闸；安全审计报告 P2-5 还给出了 URL 解析差异（`127.0.0.1\@...`）
  的更严重绕过，本报告只补充数字形式，修法以那份报告为准。**实测**（javac 调 `agentcore.jar`）：
  `check("http://0x7f000001/")`、`check("http://2130706433/")`、`check("http://[::ffff:7f00:1]/")`、
  `check("http://localhost./")` 全部返回 `null`（放行），而 `check("http://127.0.0.1/")` 返回 `LOCAL_HOST`。
- **建议修法**：host 先做数字 IPv4 规范化（`0x`/十进制/八进制/`127.1`），再判定；IPv6 统一按
  `Inet6Address`/前缀判定 `::ffff:*`、`fc00::/7`、`fe80::/10`；或直接与 iOS 共用一份更严格的策略。
