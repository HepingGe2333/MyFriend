**最该先修的三条**

1. **SSE 的 8 MB 单行上限在真实链路上永远不会触发**（`Net/OpenAICompatibleClient.swift:462-471` +
   `Net/SSE.swift:44,61-67`）。生产代码在**客户端自己**用 `buffer.append(byte)` 攒到换行才交给
   `SSEParser`，而 `SSEParser` 的超限分支只在"喂进来的 buffer 里没有换行、且长度 > 8 MB"时执行 ——
   这个前缀在生产里不可能出现。于是一个不换行、持续输出的 `text/event-stream` 会让客户端的
   `buffer` 无上限增长（`URLSession` 资源超时 120/900 秒），这就是本版声称"SSE 单行上限对齐 8 MB"
   却没有真正兜住的那一类 OOM。单测 `SSEParserTests:83-91` 测的是生产不走的入口。
2. **远程决策层的 `connect`（3 秒）超时参数完全无效**（`Core/AgentCoreClient.swift:424,496`）。
   `URLRequest.timeoutInterval` 会覆盖 `URLSessionConfiguration.timeoutIntervalForRequest`；客户端在
   `post()` 里把请求级超时设成了 `overall`（8 秒），所以"3 秒连不上就回退本机"只在注释里成立。
   本机探针实测：会话 0.4 秒 + 请求级 2.0 秒 → 2.01 秒才超时（见 P1-2）。agentd 不可达时，
   一次回复里串行调用的几次决策会各等满 8 秒，而且没有失败熔断（下次还等）。
3. **已打开的聊天页在"清空聊天 / 替换导入"之后仍显示已删消息**（`Views/Chat/ChatViewModel.swift:145-192,389-398`）。
   本版把重读改成了"只追加"（P2-5 的修法），但 `enter()` / 20 秒轮询都只会 `pageAfter(窗口最后一条)`，
   窗口里已有的、已经被别处删掉的消息永远不会被移除；`sessions.byId` 返回 nil 时也不会清空 `session`。
   触发路径：聊天页 → 简介菜单 → 设置 → "清空全部聊天与记忆" → 返回聊天页（或设置 → 备份 → 替换导入）。
   页面会一直显示已经不存在的消息，发送只会得到"会话不存在"。

## P1

### P1-1 SSE 超长行护栏名存实亡：客户端自攒缓冲无上限，`SSEParser.MAX_LINE_BYTES` 在生产路径上不可达

- **位置**：`ios/MyFriendKit/Sources/MyFriendKit/Net/OpenAICompatibleClient.swift:462-471`
  （`var buffer = Data()` → 每字节 append → 只有遇到 `0x0A` 才 `parser.feed(buffer)`）；
  `ios/MyFriendKit/Sources/MyFriendKit/Net/SSE.swift:44,54-67`（超限分支）；
  同文件 `:926-943` 的 `readAll` 上限只保护**非流式**路径。
- **触发条件**：服务端声明 `Content-Type: text/event-stream`，但持续输出**不含换行**的字节
  （坏网关、被劫持的代理、把整份 JSON 慢慢吐出来的服务、`data:` 前缀后跟一个巨大 payload 再断流）。
- **为什么错**：`SSEParser.feed` 的唯一生产调用点在 `:470`，传进去的 `buffer` 一定以 `0x0A` 结尾，
  解析器的 while 循环会先把整行消费掉，函数末尾 `if buffer.count > MAX_LINE_BYTES` 时 buffer 已空 ——
  所以 **8 MB 上限一次也不会生效**；真正增长的是客户端自己的 `buffer`，它没有任何上限。
  `URLSession` 的资源超时是 120/900 秒（`makeSession` 之外的那条聊天会话），足够在慢速链路上把
  一个几百 MB 的"单行"攒进内存（聊天会话的超时是 `App/AppEnvironment.swift:729-735` 的
  请求 120 秒 / 资源 900 秒）。`SSEParserTests:83-91` 直接 `parser.feed("data: " + 8MB)`，
  测的正是生产里不会出现的调用形态，所以单测是绿的、缺陷仍在。
  另外 Android 侧超限是"抛 `ResponseTooLong` 并中止流"，iOS 是"把缓冲当整行吐给上层解析失败"，
  行为本来就不同（文档里承认为刻意差异），但在上限不可达的前提下连"降级"都没发生。
- **修法**：在客户端的 `buffer.append(byte)` 之后加同一个上限判断（超限即 `throw ApiException("响应过长")`
  或截断并标记），或者改成每次 `parser.feed(Data([byte]))` 让解析器的上限真正生效（并顺手把解析器
  超限语义改成抛错，与 Android 对齐）；再把 `SSEParserTests` 的超限用例改成走客户端那条链路。

### P1-2 `connect` 超时参数被请求级超时覆盖：agentd 不可达时每次决策等满 8 秒，且没有熔断

- **位置**：`ios/MyFriendKit/Sources/MyFriendKit/Core/AgentCoreClient.swift:420-433`
  （`timeoutIntervalForRequest = connect(3)`、`timeoutIntervalForResource = overall(8)`）、
  `:489-501`（`request.timeoutInterval = timeouts.overall`）、`:523-545`（`Task.sleep` 赛跑）。
- **触发条件**：`MYFRIEND_AGENT_CORE=remote`（或 Info.plist 固定成 remote），baseURL 指向一台
  丢包/不可路由/正在重启的 agentd（不是"连接被拒"这种立刻报错的情况）。
- **为什么错**：Apple 的语义是请求级 `URLRequest.timeoutInterval` 覆盖会话级
  `timeoutIntervalForRequest`。`:496` 把请求级设成 `overall` 之后，`:424` 的 `connect=3s` 对这四个端点
  完全失效；所谓"3 秒等首个字节"实际是 8 秒。本机探针（`/tmp` 临时脚本，只 `accept` 不回包的
  TCP 监听）实测：`session.timeoutIntervalForRequest=0.4` + `request.timeoutInterval=2.0` →
  **2.01 秒**超时，证明覆盖关系。后果：一次聊天回复里串行经过 `sleepDecision`（`ChatService:496`）
  和可能的 `deferPlan`/`clampToolArgs`（`ChatService:606`、`ToolExecutor:662,710`），agentd 不可达时
  用户最多要多等 8×N 秒才看到模型开始回；`HeartbeatController:181` / `AgentLoop:176` 的后台拍同样
  每次白等 8 秒。没有"连续失败就暂时停用远程"的熔断，`FallbackAgentCoreClient` 每次都要先把超时等满。
- **修法**：删掉 `:496` 的 `request.timeoutInterval = timeouts.overall`（会话配置里两个值都已设好，
  `connect` 负责等首字节、`overall` 由 `Task.sleep` 赛跑兜底），或在 `post()` 里只把请求级设为
  `connect`；再给 `FallbackAgentCoreClient` 加一个"失败后 N 秒内直接走本机"的短路。

### P1-3 "只追加"的消息窗口不感知外部删除：清空聊天 / 替换导入后已打开页面继续显示已删消息

- **位置**：`ios/MyFriend/Views/Chat/ChatViewModel.swift:145-192`（`reloadMessages`：只有
  `sessions.byId` 成功时才更新 `session`；`preservingLoadedRange && messages.last != nil` 时只调
  `appendNewerMessages`）、`:183-190`（`pageAfter` 只取"最后一条之后"）、`:389-398`（20 秒轮询）；
  相关入口 `Views/Settings/SettingsScreen.swift:684`（清空聊天）、
  `Views/Backup/BackupScreen.swift:359-362`（替换导入）、`Views/Chat/ChatScreen.swift:145-162`
  （从聊天页内推设置/备份页、返回时 `enter()` 再次走"只追加"）。
- **触发条件**：打开一段聊天 → 从聊天页简介菜单进设置（或备份页）→ 执行"清空全部聊天与记忆"或
  "照备份重新接回（替换）" → 返回聊天页。
- **为什么错**：窗口以"已加载区间的最早一条"为锚、只往后追加，这是 P2-5 的正确修法；但**删除**与
  **整体替换**从来没有让窗口重置：`messages.last` 还在（它是旧对象），`pageAfter` 以已删消息的
  `(createdAt,id)` 为游标只会返回空，`messages` 原样保留。`session` 也只在"读到了"时才赋值，
  库里的会话已经没了它仍然是旧值。更糟的是 20 秒轮询的比较条件
  `latestId(nil) != messages.last?.id` 永远成立，于是每 20 秒做一次 count + pageAfter 的无效重试，
  页面永远修不好（只有退到首页让 `ChatScreen` 重建、或重启 App 才恢复）。这属于"用户能碰到、
  且本版新引入"的行为回归（0.10.2 的 `enter()` 是重读最后 N 条，清空后会自然变空）。
- **修法**：`reloadMessages` 在 `sessions.byId` 为 nil、或 `messages.count(sessionId:) == 0`、
  或全表条数**小于**窗口条数（说明有外部删除）时，走 `preservingLoadedRange: false` 重置窗口；
  顺带在轮询里对"会话已不存在"早退，别每 20 秒重试。

### P1-4 导出没有和导入对称的 64 MB 护栏：可能导出一份"自己导不回来"的备份（并伴随内存尖峰）

- **位置**：`ios/MyFriendKit/Sources/MyFriendKit/Services/BackupService.swift:171-217`
  （`export()` 一次性把全部消息读进 `[MessageEntity]`、拼 `BackupBundle`、`BackupCodec.encode` 成
  一个 `String`，**没有任何大小上限**）；`:130`（`maxImportBytes = 64 MB`）、`:259-266`
  （`importBackup` 超限直接拒绝）；`Views/Backup/BackupScreen.swift:284-300`
  （再把整串塞进 `BackupJSONDocument` 交给 fileExporter，等于再复制一份）。
- **触发条件**：聊天量大（几万条消息 / 大量工具痕迹 / 长摘要与记忆）时导出；随后在**同一台手机**
  或新手机上导入这份文件。
- **为什么错**：导出成功的备份，导入时会被 `tooLargeMessage` 拒绝 —— 用户唯一的迁移/存档手段变成
  死文件，而导出的当下没有任何提示。同时 `export()` 的"全量实体 + 整串 JSON + FileDocument"
  在大库下是 3～4 份驻留内存，比导入侧刚加的那道闸更容易先 OOM（`agentcore` 里已有给 Android 用的
  `ExportStreaming`，iOS 没接）。这条与 P2-3（导入侧已剥路径）不同：是**尺寸口径不一致**。
- **修法**：导出时也按 `maxImportBytes` 判一次并给出明确错误（或把上限提到两端一致的更大值），
  更彻底的是照 `ExportStreaming` 的做法分批写盘、避免整串驻留。

## P2

### P2-1 `remote-strict` 在 App 里没有任何可观察的失败：所有调用点都 `try?` / `catch` 回本机

- **位置**：`Chat/ChatService.swift:496-497`（sleep）、`:606-609`（defer）、
  `Services/ToolExecutor.swift:661-667`（defer）、`:709-713`（clamp）、
  `Services/AgentLoop.swift:176-179`、`Services/HeartbeatController.swift:181-184`；
  客户端本身的约定在 `Core/AgentCoreClient.swift:34-45`（"remote-strict 远程失败直接报错"）。
- **触发条件**：用 `remote-strict` 联调，agentd 没起、端口写错、或返回 500。
- **为什么错**：`RemoteAgentCoreClient` 确实把错误抛给了调用点，但**每一个**调用点都把它吞掉并改用
  `NativeAgentCoreClient`（有的只写一行日志，而 `DebugSeeding.log` 在 Release 是空实现
  `App/DebugSeeding.swift:559`）。于是"严格模式"与普通回退模式在 App 行为上没有区别，只有延迟和
  Debug 日志不同；用 `remote-strict` 做"确认 agentd 真的被用上了"的验收会得到假阳性
  （`MYFRIEND_DEBUG_AGENT_CORE_PING` 那条 Debug 自检是另一条路径，不能替代运行时判定）。
- **修法**：给 App 注入一个"严格模式失败即上抛"的开关（例如 `ChatService`/`ToolExecutor` 在
  `mode == .remote(preferredFallback:false)` 时不兜底），或把 `AgentCoreMode` 暴露给一个启动自检，
  失败时写一条用户可见/可导出的诊断日志。

### P2-2 通知深链：温启动点通知会把待打开会话留在 UserDefaults；`sessionId` 也不校验存在性

- **位置**：`ios/MyFriend/App/AppNotifications.swift:143-148`（`handleNotificationTap` 无条件
  `pendingDeepLink.stage(sessionId)`）、`ios/MyFriend/App/RootView.swift:40-53`
  （只有 `.task` 里 `consume()`，`onReceive` 分支只把 `pendingSessionId` 置 nil，不清持久化键）、
  `Support/PendingDeepLink.swift:69-71`（`clear()` 在 App 里没有调用点）。
- **触发条件**：① App 正在运行（或后台）时点通知 → 进会话；之后强制退出再冷启动 → 会**再次**跳到
  那条旧会话（因为键还在）。② 通知对应的会话已被删除（清空数据、删人格）→ 冷启动跳到一段不存在的
  会话，`ChatScreen` 显示空白页、`ChatViewModel.enter()` 拿不到 session、发送只会得到"会话不存在"。
- **为什么错**：落盘是为了"冷启动不丢"，但消费只发生在根视图首次 `.task`；温启动路径把同一份状态
  写进持久化却没有对应清理，于是"一次点击"变成了"以后每次冷启动都跳"。同时 `RootView` 直接
  `path.append(Route.chat(...))`，没有任何"这段会话还在不在"的校验（`AppEnvironment.session(forPersona:)`
  能建会话，但这里拿的是 sessionId，没有 personaId 可回落）。
- **修法**：在 `RootView.onReceive` 消费 `pendingSessionId` 的同时调用 `pendingDeepLink.clear()`；
  跳转前用 `stores.sessions.byId` 校验，不存在就丢弃并回首页（或转成"按 personaId 找/建会话"）。

### P2-3 导出仍把设备绝对路径带进备份（头像剥了、消息附件没剥）；夹具里的 `file:///` 也还在

- **位置**：`Services/BackupService.swift:771-779`（`toBackupMessage` 原样带
  `attachmentsJson: message.attachmentsJson`，而 `AttachmentsCodec` 的 `uri` 就是
  `file:///var/mobile/...`，见 `Support/Attachments.swift:21,30-31`）；`:649-660`
  （只有头像走了 `exportedAvatarUri`）；`Tests/.../Backup/BackupSamples.swift:31,135,159`
  （手写样本里仍有三个 `file:///`）；`fixtures/backup/ios-export-v2.json` 由
  `BackupInteropTests:190-215` 从**这份手写样本**重新编码写出，不经过 `export()`。
- **触发条件**：任何一次真实导出；以及 Android 侧读 `ios-export-v2.json` 的夹具测试。
- **为什么错**：`docs/CHANGELOG.md` 的 iOS 条目写的是"导出剥离设备绝对路径"，实际只剥了
  人格/预设头像；消息附件里的沙盒路径（含 App 容器 UUID）原样进了备份。同时这份"iOS 导出样本"
  夹具并不是导出代码的产物（`BackupInteropTests:190-215` 只是把 `BackupSamples` 手写的那份 bundle
  重新编码写盘），所以它既不能担保"导出无绝对路径"，也不代表当前 `export()` 的真实形状 ——
  而 Android 的 `BackupFixtureTest:117-130` 把它当跨端契约样本读。
- **修法**：`toBackupMessage` 复用一份"清空 file/绝对路径 uri，只留 `mime/width/height`"的映射
  （或干脆导出时把 `attachmentsJson` 置 nil，反正导入侧也丢弃它）；并让 `BackupSamples` 用同一套
  映射生成，重新落一次夹具。

### P2-4 导入的"读文件 + JSON 预解析"仍在主线程，而允许的上限已经是 64 MB

- **位置**：`ios/MyFriend/Views/Backup/BackupScreen.swift:322-348`（`handleImportSelection` 在主线程调
  `readBackupText` 与 `preview(fileText:)`）；`Services/BackupService.swift:235-250`
  （拿不到 `attributesOfItem` 时先 `String(contentsOf:)` 整份读，再做第二道判断）、`:222-233`
  （`preview` 在这里同步 `BackupCodec.decode` 整份 JSON）。
- **触发条件**：导入一份几十 MB 的合法备份（大聊天库），或从网络卷/文件 Provider 选文件
  （`attributesOfItem` 可能拿不到 size）。
- **为什么错**：64 MB 的 JSON 在 main runloop 上做 UTF-8 解码 + `JSONSerialization`，是秒级卡顿 +
  `String`/对象图几倍内存的尖峰；0.11.0 把上限从"无"提到 64 MB，恰好把这段主线程窗口放大了。
  `importBundle` 已经挪进 `Task.detached`，但"读 + decode"这两步没有。
- **修法**：把 `readBackupText` + `preview` 一起放进 `Task.detached`（和导出/导入一致），
  主线程只收结果；`readBackupText` 改用 `FileHandle` 按块读到上限即中止。

### P2-5 连接锁只保护写：后台长事务（备份导入）会把主线程的同步写阻塞住

- **位置**：`ios/MyFriendKit/Sources/MyFriendKit/Data/SQLiteStore.swift:176-190`
  （`withConnectionLock` 是阻塞的 `NSRecursiveLock`）、`:212-236`（`inTransaction` 整段持锁）；
  `Services/BackupService.swift:375-427`（导入的整段事务：逐条 upsert + 每条记忆现算中文词元）；
  主线程写入口例如 `Views/Chat/ChatViewModel.swift:151-158`（打开会话把未读清零）、`:581,598`
  （删消息 / 清空上下文后写回会话）。
- **触发条件**：备份导入（或"删除全部数据"）在 `Task.detached` 里跑长事务时，用户在主线程触发任何
  `upsert`/`delete`（进聊天页清未读、删一条消息、发消息……）。
- **为什么错**：0.10.2 的 P0-1 修法把"写"纳入连接锁是对的，但锁是阻塞的；导入一个几十 MB、
  上万条消息 + 每条记忆做词元切分的单事务可能持续数秒到十几秒，主线程在这段时间里会卡在
  `lock()` 上（不是 `sqlite3_busy_timeout` 的 5 秒，而是无限等），最坏触发 watchdog。
- **修法**：把导入事务切成小批（每批一个事务、批间 `await Task.yield()`），或改用 WAL 下的
  "单写者 + 读快照"；至少给主线程写路径加"导入中禁止进入聊天页/给出 loading"的交互约束。

### P2-6 读路径不参与连接锁：长事务期间能读到未提交数据（半份导入 / 已删数据）

- **位置**：`ios/MyFriendKit/Sources/MyFriendKit/Data/Stores.swift:92-114`（`fetch` 只用
  `database.prepare`，而 `prepare` 在 `SQLiteStore.swift:194-200` 明确"不加锁"）；对照
  `SQLiteStore.swift:212-236` 的事务持锁。
- **触发条件**：备份替换导入 / 清空数据的长事务执行期间，主线程或 20 秒/4 秒轮询正好读
  `chat_sessions` / `messages`。
- **为什么错**：SQLite 的事务状态是连接级的，同一连接上的 SELECT 会看到本事务**未提交**的写入。
  于是导入中途首页/聊天页可能读到"表已清空、还没灌入"或"灌了一半"的状态（配合 P2-5 的持有时间，
  窗口不小）；如果事务回滚，界面会短暂停在一个与库不一致的状态（本版的摘要/消息轮询会自愈，
  但"清空重播"之类的一次性动作不会重跑）。
- **修法**：给"会渲染的读"提供只读快照语义（`withConnectionLock` 包住一次读，或把长事务改成
  小批提交），至少让"替换导入"期间根视图进入一个明确的"正在恢复"状态而不是继续轮询。

### P2-8 `recentDialogue` 的 SQL `trim` 与 Swift `trimmingCharacters` 不同义；`latestUserMessage` 只判 `content <> ''`

- **位置**：`ios/MyFriendKit/Sources/MyFriendKit/Data/Stores.swift:877-896`（
  `length(trim(content)) > 0`）、`:902-910`（`content <> ''`）。SQLite 的 `trim()` 默认只去空格

- **修法**：把判定改成 `length(trim(content, char(9)||char(10)||char(13)||' ')) > 0`（或在 Swift
  侧统一做一次可见性判断），`latestUserMessage` 与 `countDialogue` 用同一个表达式，并加一条带

  正好在等 `tickGate`（上一次心跳还在跑）；或后台补算被取消时在等 `MemoryConsolidator` 的锁。
- **为什么错**：取消不会把自己从 `waiters` 里摘掉，前一个持锁者 `release()` 时它照样被唤醒、照样
  走完临界区 —— 包括发起一次 LLM 请求、写主动消息/通知，而此时系统时间片已经用完（进程随时会被杀，
  白花 token）。0.10.2 修的是 `LlmConcurrencyGate` 的取消（P1-11），`AsyncMutex` 这条同类问题没修。
- **修法**：`acquire()` 改 `withTaskCancellationHandler`（取消时从 `waiters` 摘除并 resume 自己，
  或直接 `throw CancellationError`），并在三个调用点 `acquire` 之后先查一次 `Task.isCancelled`。

## 建议修复顺序

1. **P1-1 SSE 上限**（改动最小、风险最高：一个坏网关就能把 App 打到 OOM）。先在客户端缓冲上加
   `MAX_LINE_BYTES`，再把超限测试改成走真实入口。
2. **P1-2 connect 超时**（删一行 `request.timeoutInterval` + 加一个失败熔断，就能让"3 秒回退"成真；
   顺带补一条能区分 connect/overall 的测试）。
3. **P1-3 已打开聊天页的外部删除**（在 `reloadMessages` 里补"会话不存在/条数变少 → 重置窗口"；
   这是"清空数据"后最容易让用户以为删除没生效的一条）。
4. **P1-4 导出/导入尺寸对称**（导出前判 `maxImportBytes` + 给出明确错误；有余力再上流式导出）。
5. **P2-2 深链清理与校验**（温启动残留 + 不存在的 sessionId；两处各几行，属于"通知点进去是空白页"
   这类一眼可见的 bug）。
6. **P2-1 严格模式的失败可见性** + **P2-16 测试守卫**（golden 覆盖四个响应、App 接线抽成可测类型；
   这两条决定下一版"联调验收"还可不可信）。
7. **P2-9 / P2-10 契约细节**（`marksRead` 缺省推导、`asleep` 与 Kotlin 对齐）——各一行，但属于
   跨端语义，越晚改越难。
8. **P2-3 / P2-4 / P2-5 / P2-6 备份与锁**（导出剥附件路径并重落夹具；导入的读+预览移出主线程；
   导入事务分批；至少给"恢复中"一个明确的 UI 状态）。
9. **P2-7 / P2-8 / P2-13 / P2-14 长会话与边界**（`RecallService` 窗口化、trim 统一、`focus` 封顶、
   `ImagePicking` 回退 `Data`）。
10. 其余 P2（P2-11 远程加固、P2-12 首页死代码/Timer、P2-15 定向 UPDATE、P2-17 i18n 扫描面、
    P2-18 `AsyncMutex` 取消）按常规清理排期即可。
