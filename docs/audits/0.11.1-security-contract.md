## 安全问题（P0 / P1 / P2）

### P1-1 `agentd` 无读超时 + 默认单线程 dispatch：一个半开连接可以无限期卡死整个服务

**位置**

- `agentd/src/main/kotlin/com/yap/agentd/Server.kt:16`（`HttpServer.create(InetSocketAddress(host, port), 0)`，**没有** `server.executor = …`；
  JDK 在 executor 为 null 时用 `start()` 创建的那**一个**线程串行处理所有请求）
- `agentd/src/main/kotlin/com/yap/agentd/Server.kt:24`（同步 `exchange.requestBody.use { it.readBytes() }`，没有读超时、没有大小上限）
- 文档现状：`agentd/README.md:291-297` 只写了"没有鉴权 / TLS / 限流 / 请求大小上限"，**没写没有超时、串行处理**

**触发条件**（本轮实测）

```text
1) 建立 TCP 连接，发头 "POST /v1/core/tool-args … Content-Length: 1000" + 半截 body，然后不发了；
2) 另一条连接 GET /health → 3.01s 超时（TimeoutError）；
3) 关掉第 1 条连接 → /health 立刻 200（0.00s）。
```

发起方：本机任意 App（回环）；若按 README 的"真机联调用 `--host 0.0.0.0`"部署，则是**同一局域网任意主机**。

**影响**：`agentd` 无鉴权，任何人一条连接就能让 4 个决策接口永久不可用；服务没有自愈（不会踢掉慢客户端）。
对开了远程模式的客户端表现是"每次决策 1.5s 超时后回退进程内"（聊天变慢、日志刷 warn），且**真实故障被回退掩盖**。

**修法**：`start()` 里设 `server.executor = Executors.newFixedThreadPool(4)`（或 cached pool），并设
`sun.net.httpserver.maxReqTime` / `maxRspTime`（或换成带读写超时的最小实现）；README 的"没做"清单补两条。

### P2-1 `agentd` 请求体/响应都没有大小上限：整份读进内存，还把客户端内容原样吐回去

**位置**：`agentd/src/main/kotlin/com/yap/agentd/Server.kt:24`（`readBytes()` 无上限，读之前不看 `Content-Length`）；
回显路径见 `agentd/src/main/kotlin/com/yap/agentd/Api.kt:59`（错误体拼 `invalid.message`）、`:67`（拼整条 path）、
`:139`（`LinkedHashMap(args.fields)` 原样复制并回显）、`:156`（拼整条工具名）。

**触发条件与实测**

- `POST /v1/core/tool-args`，body = `{"tool":"remember","args":{"content":"<8MB>"}}` → **200，响应 8,388,646 字节**（内容原样回显）；
- body = `{"tool":"<2MB 工具名>","args":{}}` → **400，响应 2,000,115 字节**（`不认识的工具：<2MB>`）；
- 1000 字符的路径 → 404 响应 1,065 字节（同一条反射）。

**影响**：单请求即可让 JVM 分配与请求等量的堆（`readBytes` 之后还有 `String`、解析树、回显串的副本），
GB 级 body 会 OOM（`OutOfMemoryError` 是 `Error`，`Api.kt:60` 的 `catch (Exception)` 接不住）；
错误回显让"发 1 份收 1 份"变成不设上限的双向带宽/内存放大。默认回环 + 无副作用的服务，所以记 P2。

**修法**：`Server.kt` 读前检查 `Content-Length` 与累计字节，超过 1MB 直接 413（新增 `content_too_large` 错误码），
错误文案里的客户端输入截断到 64 字符；README 的"没做"清单把"request size cap"从"坦白"升级成"已修"。

### P2-2 `agentd` 的错误体会把异常文本带出去（500 分支）

**位置**：`agentd/src/main/kotlin/com/yap/agentd/Api.kt:61`
（`errorResponse(500, "internal_error", "服务内部错误：${unexpected.message ?: unexpected::class.simpleName}")`）。

**触发条件**：任何未被 `ApiFailure` / `JsonParseException` 接住的内部异常（当前的 4 条路由与 64 层 JSON 限制下我没能构造出来；
这是**防御性**发现，`Server.kt:38` 的兜底 500 反而是干净的固定文案）。

**影响**：一旦未来某条路径抛异常，内部类名/消息会出现在 HTTP 响应里（也进入客户端 `LogcatAgentCoreLogger` 的 warn 日志）。
属于"以后会踩"的信息泄漏面。

**修法**：500 只回固定文案 + 一个随机 `errorId`，异常细节只写服务端日志（或干脆不回）。

### P2-3 iOS：附件删除没有"只删自己目录"的守卫，`AttachmentLocation.resolve` 又接受任意已存在路径

**位置**

- 删除：`ios/YapKit/Sources/YapKit/Support/MediaStorage.swift:472-479`
  （`delete(_:)` → `fileURL(for:)` → `removeItem`，**没有**目录前缀检查；对照头像的 `deleteFileIfOwned` `:496-504` 是有的）
- 路径解析：`ios/YapKit/Sources/YapKit/Support/MediaStorage.swift:263-291`
  （`:278-283`：`file://` 且路径存在 → 直接返回；`:286-289`：无 scheme 的相对路径 → `directory.appendingPathComponent(url.path)`，
  不标准化、不检查 `..`）
- Android 的对照实现：`agentcore/src/main/kotlin/com/yap/app/domain/MediaOwnership.kt:29-35` +
  `app/src/main/java/com/yap/app/util/MediaStorage.kt:238-252`（删前 `isWithin`）

**触发条件与实测**（在 `/tmp` 的 iOS 副本里加临时探针测试，跑的是真实 `MediaStorage`）

```text
MediaStorage(directory: <tmp>/attachments)
目录外存在 <tmp>/yap.db
1) storage.exists(uriString: "../../yap.db")        → true   （被当成「头像文件还在」）
2) storage.delete(MessageAttachment(uri: "../../yap.db", …)) → 文件真的被删了
```

**今天为什么还打不到**（重要，避免高估）：iOS 导入**会把** `attachmentsJson` 丢掉
（`ios/YapKit/Sources/YapKit/Services/BackupService.swift:786-800` 的 `toEntity` 写 `attachmentsJson: nil`），
所以外部输入进不了这张表；`mergeMessageIntoLocal`（`BackupService.swift:593-600`）里"本机没有、备份里有就补上"的分支
因为上游已经置 nil 而**是死代码**。聊天图片只由 `MediaStorage.saveImage` 生成，路径可信。

**影响**：这是一条"数据即代码"的潜伏破坏面：只要那个死分支被启用、或将来有别的路径（旧版本迁移、手工改库、
同步功能）往 `attachmentsJson` 写外部路径，"删一条消息 / 清空聊天"就会删掉沙盒里任意文件（数据库、prefs、别的附件）。
Android 侧 0.10.2 P2-2 已经补上了，iOS 没有跟上——也意味着两端同一个动作的安全性不同。

**修法**：`delete(_:)` 改成和 `deleteFileIfOwned` 同一个前缀守卫（或让 `fileURL(for:)` 返回前先做
`standardizedFileURL` + 目录前缀检查，一处收口）；顺手把 `BackupService.swift:593-600` 的死分支删掉或加注释说明。

### P2-4 iOS：备份导入的头像路径接受绝对路径与 `../` 穿越，且会原样落库

**位置**

- 校验：`ios/YapKit/Sources/YapKit/Services/BackupService.swift:289-301`
  （只判断 `avatarFileExists(uri)`，该闭包默认是 `MediaStorage.exists`，见 `:150`）
- `MediaStorage.exists`：`ios/YapKit/Sources/YapKit/Support/MediaStorage.swift:484-490` → `AttachmentLocation.resolve`（`:263-291`）
- 对照 Android：`agentcore/src/main/kotlin/com/yap/app/domain/BackupAvatarPath.kt:47-55`（含 `..` 直接拒绝）+
  `app/src/main/java/com/yap/app/util/MediaStorage.kt:209-218`（只取文件名 + `MediaOwnership.isWithin` 二次确认）

**触发条件**：导入一份 `personas[].avatarUri = "../../yap.db"`（或任意绝对 `file://`，指向存在文件即可）的备份。
本轮实测 `MediaStorage.exists("../../yap.db")` 返回 `true`（P2-3 的探针），即该值会被保留进 `persona.avatarUri`。

**影响**：① 头像永远加载不出来（界面破图，且用户看不出是"备份带来的坏路径"）；
② 把"沙盒内任意文件"绑成头像引用——今天不会读/传出去（头像不进提示词、不导出二进制），`deleteFileIfOwned` 也会拒绝删它，
所以不是泄漏；但两端对同一份备份的行为不同（Android 归一成文件名并拒绝越界），而且 iOS 的校验实际上等于没校验。

**修法**：iOS 抄 Android 的 `BackupAvatarPath`：取值只允许裸文件名（或 `..`/绝对路径直接判空），
再拼 `attachments/avatar-*` 后做目录前缀检查；补一条"导入带 `../` 的 avatarUri 会被清空 + warning"的单测。

### P2-5 `WebUrlPolicy` 可被"URL 解析差异"与数字 IP 形式绕过（且 iOS 没有同一套规则）

**位置**：`agentcore/src/main/kotlin/com/yap/app/domain/WebUrlPolicy.kt:51-72`（`isLocalHost`）、`:84-95`（`hostOf`）；
使用点 `app/src/main/java/com/yap/app/network/DeepSeekWebTools.kt:100-106`；
iOS 对照 `ios/YapKit/Sources/YapKit/Net/WebToolsClient.swift:462-472`（只判 scheme + host，**不判**内网字面量）。

**实测**（`javac` 直接调 `agentcore.jar`，`check()` 返回值）

| 输入 | 结果 | 说明 |
| --- | --- | --- |
| `http://127.0.0.1:8080\@example.com/` | **ALLOW** | `hostOf` 取最后一个 `@` 之后 → `example.com`；但 WHATWG 把 `\` 当 `/`，真实 host 是 **127.0.0.1:8080** |
| `https://localhost./`、`https://LOCALHOST./admin` | **ALLOW** | `localhost.`（FQDN 尾点）解析到回环，`isLocalHost` 没去尾点 |
| `http://2130706433/`、`http://0x7f000001/`、`http://0177.0.0.1/` | **ALLOW** | 十进制/十六进制/八进制 IPv4 都是 127.0.0.1，`looksLikeIpv4` 只认"数字+点" |
| `http://[::ffff:7f00:1]/` | **ALLOW** | IPv4-mapped 回环的十六进制写法；只挡了 `::ffff:127.` 文本形式 |
| `http://user:pass@example.com/` | **ALLOW** | userinfo 里的口令会被原样发给第三方抓取服务并进它的日志 |
| `http://127.0.0.1.nip.io/`、`http://localtest.me/` | **ALLOW** | 域名解析到回环；按注释"只挡字面量"是设计取舍，但与"拒绝本机/内网"的表述不一致 |
| `http://exa mple.com/`、`http://example.com\t/` | **ALLOW** | 非法 host 字符没有校验，只是转手给服务端 |
| `javascript:` / `JaVaScRiPt:` / `file:` / `tel:` / `//host` / `https:///path` | 拒绝 | 这些没问题（见"已验证不成立"） |

**触发条件**：模型生成的 `web_fetch` URL（工具参数由模型给，也间接可由网页内容/用户输入影响）。

**影响**：抓取发生在 DeepSeek 服务端，**不是设备侧 SSRF**，所以拿不到用户本机数据；但：
（a）这道闸宣称"拒绝本机/内网"，实际放过多种等价写法，等于把"让第三方服务去访问某内网地址"的请求照发；
（b）`userinfo` 里的凭据会随 URL 发给第三方（如果网页/提示词里出现了带凭据的 URL）；
（c）iOS 根本不挡内网字面量 → 同一句话里的同一个 URL，Android 报错、iOS 照发。

**修法**：host 先做规范化再判（小写、去尾点、`URL` 解析而不是手切；对 `\\` 当成 `/` 处理或直接拒绝含 `\` 的 authority）；
内网判定改为"`InetAddress` 解析后 `isLoopback/isSiteLocal/isLinkLocal`"（或至少补数字/十六进制/`::ffff:` 形式），
拒绝带 userinfo 的 URL；iOS 的 `validatePageUrl` 复用同一套规则并可加 `spec/` 用例。

发送会被拒（Android `ChatRepository.kt:394` `SESSION_NOT_FOUND`；iOS `ChatService.swift:379-381` "会话不存在"），不会建行、不会崩。
剩下的实际影响是：任意应用可以把 App 强推到某个会话页、并触发 `markRead`（`app/src/main/java/com/yap/app/ui/screens/chat/ChatViewModel.kt:324-328`）/撤销通知，属于 UI 层面的可控性，记 P2。

**修法**：两端在消费前用"会话存在"过滤（不存在就丢弃并记录），Android 再加一层
`intent.action`/显式组件 + 自定义 signature 权限，或改成只在 `PendingIntent` 里带一次性 token；
iOS 的 `PendingDeepLink` 同样在 `consume()` 时校验存在性。

| --- | --- | --- | --- |

## 已验证不成立（专门查过、结论不是缺陷）

1. **`agentd` 路由可被路径穿越/编码绕过**：不成立。实测 `/health/`、`//health`、`/%68ealth`、`/v1/core/../health`、
   `/v1/core/%2e%2e/health`、`/HEALTH` 全部 4xx；路由是 `AgentdApi.kt:34-37` 的精确字符串匹配
   （`rawPath.substringBefore('?')`，不解码、不规范化），失败方向是"拒"而不是"放"。
   方法也收口：`/health` 上除 GET 外全部 405，四个核心路径除 POST 外全部 405。
2. **超深 JSON 打挂 `agentd`**：不成立。1000 层嵌套 → `400 invalid_json`（"JSON 嵌套过深（> 64 层）"），
   堆栈不溢出（`Json.kt:45` `MAX_DEPTH=64`、`:136-137` 深度检查）。
3. **超大数字 / 浮点炸解析器**：不成立。10 万位的 `importance` → `400 invalid_argument`（`JsonValue.Num.asInt` 返回 null，
   不抛 `NumberFormatException`）。
4. **`agentd` 会被诱导执行任意决策并产生副作用**：不成立（按设计）。四个接口只调 `InProcessAgentCore` 的纯函数，
   不碰 DB/文件/网络/时钟（`defer-plan` 的 `now` 由客户端给），服务端无可变状态；能"诱导"的只是让它算一个攻击者指定的决策结果，
   没有可利用的落库/外发路径。
5. **iOS 远程客户端可被 release 包里的环境变量劫持**：不成立（就 0.11.1 的发布形态而言）。
   `AgentCoreClientFactory` 读 `YAP_AGENT_CORE` / `YAP_AGENT_CORE_URL`（`Core/AgentCoreClient.swift:761-786`），
   但真机上第三方无法给 App 注入环境变量（`SIMCTL_CHILD_*` 只对 `simctl launch` 的模拟器进程生效；
   真机要注入得能调试/越狱启动）；`Info.plist` 里也没有 `MFAgenCoreMode` / `MFAgenCoreBaseURL` 两个键
   （`grep ios/Config ios/YetAnotherPal.xcodeproj` 均为 0 命中），运行期也没有用户可见开关。所以默认 `native` 是真的默认。
   （默认 base URL 是 `http://127.0.0.1:8788`，Release 的 ATS 只开了 `NSAllowsLocalNetworking`；远程模式指向**局域网** http 地址时
   ATS 是否放行本轮未在真机验证，标为未验证。）
6. **Android 远程开关可被运行期/环境变量改写**：不成立。`BuildConfig.AGENT_CORE_REMOTE` 是编译期常量（生成物实读为 `false`），
   没有 `SharedPreferences`/intent/广播能改它；`-PagentCoreBaseUrl` 只影响构建。
   （唯一相关的小问题：`app/build.gradle.kts:65-68` 把属性值直接拼进生成的 Java 字符串字面量，没转义引号/反斜杠；
   能改构建参数的人本来就能执行任意 Gradle 脚本，所以不构成提权，最多是"URL 里带 `"` 会构建失败"。）
7. **备份头像可用 `../` / 绝对路径 / URL 编码做目录穿越**：不成立（Android）。
   `BackupAvatarPath.fileName` 先拒绝含 `..` 的整条路径，再取最后一段、过 `isSafeName`（拒 `/`、`\`、`..`、超长），
   `File(dir, name)` 不作百分号解码，最后还有 `MediaOwnership.isWithin` 二次确认。
   实测：`../../databases/yap.db` → null；`/data/.../yap.db` → `yap.db`（在 avatars 目录里找不到 → null）；
   `%2e%2e%2fdatabases%2fyap.db` → 当字面文件名（不存在 → null）；`C:\windows\x.jpg` → null。
   `file:///.../avatars/../../../databases/yap.db` 的 `portable()` 会取到 `yap.db`（只影响"导出一个名字"，无路径泄漏，见 P2-11）。
8. **Android 的媒体归属守卫可被符号链接 / `..` / 同前缀目录绕过**：不成立。
   实测 `MediaOwnership.isWithin`：目录内文件 true；`../secret.txt` false；`sub/../a.jpg` true（规范化后仍在目录内）；
   avatars 里的符号链接指向目录外 → **false**（`canonicalFile` 把链接解开）；`/tmp/probe/avatars2/x.jpg` false（前缀相同但不是子目录）。
9. **导入备份可劫持已有 API 配置的地址/明文开关（0.10.2 P1-0）**：已不成立（两端都修了）。
   Android `mergeInto` 保留本机 `baseUrl`/`webToolsBaseUrl`/`allowInsecureHttp` 并给 warning；iOS 同构，
   新配置 `allowInsecureHttp` 强制 false。**残留**：新配置仍接受备份里的 `baseUrl`（两端 `toNewEntity`），
   但 Key 留空、需要用户自己填，且导入摘要会列出配置——按"用户要主动选这条配置并填 Key"评估，不升级为发现。
10. **iOS 导入 `attachmentsJson` 后删消息会删任意文件**：今天不成立（但守卫仍缺，见 P2-3）。
    `BackupService.toEntity` 把 `attachmentsJson` 置 nil（`:786-800`），所以 `mergeMessageIntoLocal` 的"备份里有就补上"分支拿到的永远是 nil
    → 备份内容进不了库。我是按"证据不足就不算漏洞"处理的，只记 P2 + 潜伏风险。
11. **iOS 删头像会删到附件目录外的文件**：不成立。头像走 `deleteFileIfOwned`（`MediaStorage.swift:496-504`），
   先 `standardizedFileURL` 再比目录前缀；外来的 `../`/绝对路径会被拒绝。
12. **通知正文在锁屏泄漏**：不成立（Android）。`ChatNotifier` 用 `VISIBILITY_PRIVATE` + `publicVersion`，
   锁屏公开版只有 App 名 + "他给你发来一条消息"（`util/ChatNotifier.kt:49-78,166-180`）；iOS 的通知 body 永远是固定文案，
   `userInfo` 只有 session/persona id（`App/AppNotifications.swift:100-140`）。
13. **深链能越权读别人/写数据**：不成立（单用户本地库 + 发送前校验，见 P2-7 的影响段）；未知会话在两端都不会被创建。
14. **`spec/agent-core/cases/*.json` 的 `file` 字段是"测试读路径"**：不成立。两端测试只读 `cases`/`inputSpec`/`tolerance`
    （`AgentCoreSpecTest.kt:75-94`、`AgentCoreSpecTests.swift:41-61`），`file`/`symbol` 是文档字段；本轮 Android 6 例 / iOS 6 例全绿，
    与 `file` 指向哪里无关。
15. **两端 AgentCore 契约字段名漂移**：不成立（本轮全绿）。iOS 的 golden（`AgentCoreClientTests.swift:647-700`）**直接解析**
    `agentcore/.../AgentCoreProtocol.kt` 的常量并与实际编码字段比对，本轮通过且未 skip；`/v1/core/*` 路径常量也一致。
16. **备份 `BackupSession` 仍多 6 个 sync 字段（0.10.2 P1-5）**：不成立（已修）。脚本比对 11 个 `Backup*` 结构字段集合完全相同，
    v2 fixture 的 `sessions[0]` 只剩 18 个契约字段。
17. **i18n 守卫是"假守卫"**：不成立。真中文、占位符类型变化、删 key、新增死键在两端都会红（见 P2-10 的红绿表），
    只有特定几类缺口。
18. **`web_fetch` 的相对协议/混合大小写 scheme 能过**：不成立。`javascript:`、`JaVaScRiPt:`、`tel:`、`//host`、`file:`、`https:///path`
    实测全部拒绝（大小写已 `lowercase()`）。
19. **备份导入大小上限两端不一致**：不成立。都是 64MB，且 Android 是"文件大小预检 + 有界读取 + 解析前字符数"三道、
    iOS 是"文件属性 + UTF-8 字节数"两道（`BackupLimits.kt`、`BackupService.swift:237,247,261`）。
20. **"远端不可达 → 静默回退"本身**：按设计接受，且文档写到了
    （`README.md:155`、`agentd/README.md:105-110`、`docs/ARCHITECTURE.md:159`）：Android 每次失败写
    `YapAgentCore` warn 并回退，iOS 回退时写一行日志；默认 `remote=false`/`native` 时根本不构造网络客户端
    （`core/AgentCoreClient.kt:206-222`、`Core/AgentCoreClient.swift:807-830`）。

    它不是"偶尔连不上"，而是"永远连不上但没人看得出来"，建议在构建脚本里直接拒绝这种组合。
21. **iOS 附件目录的"不进整机备份"标记在清空数据后是否仍成立**：是（0.10.2 P1-8 的修复有效）。`MediaStorage.init` 与
